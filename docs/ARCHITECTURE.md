# Архитектура PTZ Tracker

Программа для Windows (PySide6): управляет PTZ-камерами Panasonic AW-HE42 по HTTP, принимает их видео по сети, находит людей нейросетью и ведёт выбранного человека камерой. Разработка ведётся на macOS: живая камера с машины разработчика недоступна, всё проверяется на симуляторе. Реальные факты приходят от пользователя через «Диагностику камеры».

## Карта модулей (`src/ptztracker/`)

| Пакет | Ответственность | Главные типы |
|---|---|---|
| `config.py` | Настройки в `%APPDATA%\PTZTracker\config.json`, атомарная запись, пароли в `keyring` | `CameraConfig`, `AppConfig`, `ConfigStore` |
| `camera/` | Всё о камере: команды Panasonic, HTTP, очередь команд, сессия одной камеры, замеры HE42 | `protocol`, `CameraClient`, `CommandScheduler`/`Priority`, `CameraSession`, `he42` |
| `video/` | Приём кадров: RTSP/MJPEG через PyAV, подбор рабочего адреса | `Frame`, `FrameSource` (Protocol), `RtspSource`, `stream_urls` |
| `vision/` | Люди на кадре: детектор позы (ONNX), сопровождение и цель, фоновый анализ | `PoseDetector`, `SimDetector`, `PersonTracker`, `Analyzer`, `AnalysisResult` |
| `control/` | Слежение: модель камеры, композиции, усилие, регулятор, поток слежения, мастер калибровки | `Calibration`, `FramingController`, `Follower`, `CalibrationRunner` |
| `sim/` | Виртуальная AW-HE42: та же HTTP-команда, динамика по замерам, синтетическая сцена с разметкой | `SimPtz`, `SimHttpServer`, `SimFrameSource`, `SyntheticStage` |
| `diagnostics/` | Диагностика на площадке → zip-отчёт; общий замер скорости | `run_diagnostics`, `checks`, `probe` |
| `ui/` | Окна Qt: главное окно, превью с рамками и зонами, панели. `theme.py` — единственный источник цветов (держит `test_no_hardcoded_colors`) и основных размеров; `widgets.py` — общие элементы (`StateTile`, `Chip`, `KeyButton`, `VideoFrame` с рамкой Tally); `state.py` — чистые функции «что показать» (`tracking_view`, `tally_chip`); `atem_dialog.py` — настройки ATEM | `MainWindow`, `PreviewWidget`, `FollowPanel`, `StateTile`, `AtemDialog` |
| `tally/` | Клиент Tally микшера ATEM по UDP, без Qt: фоновый поток, неизменяемый снимок | `AtemTally`, `TallySnapshot`, `atem_input_of` |
| `models/` | Модель YOLO11n-pose (ONNX, AGPL-3.0) | `POSE_MODEL_PATH` |

Зависимости идут сверху вниз: `ui` → `control`/`vision`/`camera` → `video`/`sim`. `camera/he42.py` — единственный источник замеров живой камеры (скорости, разгон, задержки). Его читают и `sim`, и `control.camera_model`. Расхождение этих двух мест уже однажды сломало проверку регулятора.

## Поток данных

```
камера ──HTTP #PTS/#Z/#APC…── CommandScheduler (≥130 мс между командами, приоритеты, склейка по ключу)
   │                                   ▲              ▲                       ▲
   └─MJPEG/RTSP→ FrameSource ─latest()→ Analyzer ─AnalysisResult→ Follower ──┘   ручные команды (UI → CameraSession)
                      │                (поток)        │            (поток 25 Гц)
                      └──────────── PreviewWidget ◄───┘ (таймер Qt, только читает)
```

- **Tally (ATEM):** микшер → UDP 9910 → поток `atem-tally` (`AtemTally`) → `snapshot()` → таймер Qt 100 мс в `MainWindow` → рамка видео и чип. Состояние «в эфире / в предпросмотре» известно только после того, как с последнего hello пришёл TlIn; пока его нет, снимок «неизвестно». Запоздалый или повторный старый TlIn не применяется: флаги берутся только из пакета новее последнего применённого (номера 15-битные, с переносом). Для защиты эфира в основной ветке — `safe_to_move(вход)`: True, только если состояние входа известно (`TallySnapshot.known`) и он не в эфире. `tally()` для этого не годится: его None значит и «не в эфире», и «неизвестно». Камера в эфире не должна двигаться без явного разрешения.
- **`CameraSession`** собирает всё для одной камеры: клиент, планировщик, источник кадров, анализ, слежение. Несколько камер в будущем — это несколько сессий.
- **Потоки:**
  - планировщик команд;
  - приём видео;
  - анализ;
  - слежение (25 Гц) плюс опрос зума;
  - проверка связи;
  - Tally ATEM (`atem-tally`, UDP 9910);
  - симулятор (HTTP и физика).

  Интерфейс читает их состояние таймерами (`MainWindow._sync_follow`, `_update_status`, `_sync_tally`) и сам никогда не ждёт сеть или нейросеть.
- **`Analyzer.latest()` и `Follower.output`** — неизменяемые снимки: UI их только читает. Трекер меняется только под замком анализатора.

## Единицы и знаки (сквозные)

- **Координаты** в регуляторе — доли кадра (0…1).
- **Скорости:**
  - pan — fw/s, доли ширины кадра в секунду;
  - tilt — fh/s, доли высоты (в коды переводится через `TILT_FROM_FH = 9/16`);
  - зум — ln(масштаба)/с.
- **Коды скорости камеры** 01–99, 50 = стоп. Pan > 50 — вправо, tilt > 50 — вверх, zoom > 50 — к теле.
- **Регулятор в «мировых» единицах:** смещение от центра, делённое на масштаб зума. Иначе наезд выглядел бы как ходьба человека.
- **Размер человека** — U, вертикаль «нос → линия плеч», не меньше 0,375 ширины плеч. Опорная точка — над серединой плеч. Наклон и поворот головы камеру не двигают.
- **`Frame.t_capture`** — момент получения кадра программой, а не съёмки. Задержку видео вычитает регулятор: `Calibration.video_latency` по типу потока.

## Инварианты безопасности (эфир)

1. Любое ручное действие (джойстик, зум, стрелки, пресет, фокус), Esc, смена камеры, остановка анализа (результат старше 0,6 с + задержка видео) или раскачка (сторож) **выключают слежение немедленно**. Стопы `#PTS5050`/`#Z50` уходят с приоритетом MANUAL, ручная команда в ту же ячейку их заменяет.
2. Аварийные стопы никогда не отбрасываются (`er2` повторяется, EMERGENCY не ограничен ретраями). Разовые команды (пресет, разовый AF) устаревают через 2 с без связи.
3. Цель потеряна — камера плавно останавливается (~0,5 с) и ждёт. Слежение при этом остаётся включённым.
4. `CameraSession.stop()` не подвешивает UI: стопы ждём, только если камера на связи. Потоки, застрявшие в сети, — daemon.
5. Кнопка «СТОП КАМЕРЫ» равна Esc: выключает слежение до стопа и не зависит от состояния Tally.
6. Пароли не попадают в лог, на экран и в отчёт диагностики (`redact_url`, `mask`).

## Регулятор (кратко; детали и причины — `docs/DECISIONS.md`)

`FramingController.step()` — чистая функция шага, тестируется в виртуальном времени (`tests/control/loop.py`). По каждой оси:
- компенсация задержки по модели камеры (`CameraDynamics`: мёртвое время + инерция τ);
- скорость человека — наклон за 0,4 с, упреждение с весом 0,5;
- мёртвая и мягкая зоны с гистерезисом; трогаемся, только когда человек вышел из мёртвой зоны;
- медленная доводка после перелёта;
- ограничение ускорения;
- сторож раскачки.

Зум: наезд одним движением, когда человек стоит ≥ 1 с; отъезд сразу у края кадра; поворот подстраивается под наезд. `Follower` переводит скорости в коды по `Calibration` (таблица «код → fw/s» по зумам) и шлёт через планировщик: TRACKING для поворота, TRACKING_ZOOM для зума (поворот важнее).

## Тесты

- **Быстрый набор** `pytest -m "not slow"` — около минуты: протокол, планировщик, модели, регулятор в виртуальном времени, UI на offscreen-Qt.
- **`slow`** — реальное время на симуляторе: замкнутый контур, слежение, калибровка, диагностика. Полный прогон ~9 мин. Под нагрузкой эти тесты изредка нестабильны; это граничные метрики, а не логика.
- **Виртуальный стенд** `tests/control/loop.py` умеет: рассогласование скорости камеры (`speed_factor`), задержку очереди (`cmd_delay`), зум у края объектива. Новые свойства регулятора проверяются сначала им.

## Известные слабые места

- `ui/main_window.py` (~640 строк) собирает слишком много: список камер, горячие клавиши, связь панелей со слежением. Кандидат на разделение при следующем расширении UI.
- **Симулятор совпадает с моделью регулятора по построению.** Ошибки калибровки на нём не видны, их ловит только виртуальный стенд с `speed_factor`.
- **У конфига нет номера версии схемы.** Новые поля добавляются со значениями по умолчанию; переименование полей потребует миграции.
- **Нет проверки типов (mypy).** Регресс по типам ловят тесты; numpy-числа из ключевых точек уже однажды сломали арифметику со знаками.
