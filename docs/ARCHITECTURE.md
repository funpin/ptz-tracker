# Архитектура PTZ Tracker

Программа для Windows (PySide6): управляет PTZ-камерами Panasonic AW-HE42 по HTTP, принимает их видео по сети, находит людей нейросетью и ведёт выбранного человека камерой. Разработка ведётся на macOS: живая камера с машины разработчика недоступна, всё проверяется на симуляторе. Реальные факты приходят от пользователя через «Диагностику камеры».

## Поток данных

```
камера ──HTTP #PTS/#Z/#APC…── CommandScheduler (≥130 мс между командами, приоритеты, склейка по ключу)
   │                                   ▲              ▲                       ▲
   └─MJPEG/RTSP→ FrameSource ─latest()→ Analyzer ─AnalysisResult→ Follower ──┘   ручные команды (UI → CameraSession)
                      │                (поток)        │            (поток 25 Гц)
                      └──────────── PreviewWidget ◄───┘ (таймер Qt, только читает)
```

- **Tally (ATEM):** микшер → UDP 9910 → поток `atem-tally` (`AtemTally`) → `snapshot()` → таймер Qt 100 мс в `MainWindow` → рамка видео и чип. Состояние «в эфире / в предпросмотре» известно только после того, как с последнего hello пришёл TlIn; пока его нет, снимок «неизвестно». Запоздалый или повторный старый TlIn не применяется: флаги берутся только из пакета новее последнего применённого (номера 15-битные, с переносом). Tally только визуальный: он ничего не блокирует (решение пользователя). `safe_to_move(вход)` оставлен на будущее — True, только если состояние входа известно и он не в эфире; `tally()` для блокировки не годится, его None значит и «не в эфире», и «неизвестно».
- **`CameraSession`** собирает всё для одной камеры: клиент, планировщик, источник кадров, анализ, слежение. Камер до четырёх — это до четырёх сессий в клетках `CameraGrid` (сетка 2×2); у каждой свой планировщик, поэтому команды разных камер друг друга не задерживают.
- **Питание и изображение** (`CameraSession.power`, `.image`) — из ответов, которые планировщик и так получает (слушатель `add_sent_listener`): пульс `#O` раз в 2 с → `on | standby | switching | unknown`, gain/WB/температура — опрос раз в ~10 с и эхо команд. В `standby`/`switching` ручные команды и gain/WB не ставятся в очередь (камера ответила бы ER2, а er2 планировщик повторяет); аварийный стоп идёт как всегда. Признак standby — только `#O`: MJPEG у HE40 в ожидании продолжает идти. UI читает снимки по таймеру.
- **Потоки:**
  - планировщик команд;
  - приём видео;
  - анализ;
  - слежение (25 Гц) плюс опрос зума;
  - проверка связи;
  - Tally ATEM (`atem-tally`, UDP 9910);
  - симулятор (HTTP и физика).

  Интерфейс читает их состояние таймерами (`MainWindow._sync_follow`, `_update_status`, `_sync_tally`) и сам никогда не ждёт сеть или нейросеть.
- **`Analyzer.latest()` и `Follower.output`** — неизменяемые снимки: UI их только читает. Трекер меняется только под замком анализатора.

## Несколько камер (`multicam/`, `ui/main_window.py`)

- **Выбранная клетка.** Одна из клеток выбрана (рамка, правая панель, клавиатура, кнопки интерфейса действуют на неё). Выбор другой клетки ничего не останавливает: слежение, флажки агента и ручные команды остальных камер остаются как были.
- **Скорость на камеру.** У каждой клетки свой `VelocityMixer`: источники (клавиатура, мышь, геймпады) складываются, сумма ограничена ±1. Любое ручное действие выключает слежение только той камеры, которую двигали, до отправки её следующей команды. Esc, аварийный стоп и закрытие окна идут по всем клеткам (`emergency_stop_all`; один сбой не прерывает остальных).
- **Анализ.** Нейросеть крутится не на всех камерах: число «одновременно анализируемых» (`max_analyzed`, меню ☰, по умолчанию 1) делит `allocate_analysis`: сначала камеры со слежением (их не отнимают), потом назначенные оператором (`AppConfig.analysis_ids`: клик по «БЕЗ АНАЛИЗА» в шапке или TRACK на камере без анализа), потом остальные по порядку клеток. Выбор клетки (мышь, клавиши, главный геймпад) анализ не двигает — решение пользователя 2026-11-06. Включение TRACK сверх лимита или на камере, где слежение выключено в настройках, `tracking_refusal` отклоняет с понятным текстом; у камеры без анализа слежения нет (нет `Follower`). Камера может быть исключена из слежения настройкой камеры.
- **Агент.** `AgentGate` держит оба флажка отдельно для каждой камеры. API принимает `camera` (id или номер клетки 1–4); без него — выбранная клетка.
- **Режим `--sim`.** Открывает две виртуальные камеры, sim1 и sim2.

## Геймпад (`gamepad/`, `ui/gamepad_bridge.py`, `ui/camera_menu.py`, `ui/hotkeys_dialog.py`)

Путь намерения: поток опроса (`GamepadThread`, SDL) → `Mapper.update` → намерения (`PanTilt`, `Zoom`, `Preset`, `IrisStep`, `GainStep`, `Neighbor`, `ToggleFollow`, `Stop`, …) → сигнал в поток Qt (`GamepadBridge.intents`, `QueuedConnection`) → `MainWindow._on_pad_intents` → те же методы сессии, что у клавиатуры. Новых путей к камере нет, поэтому «ручное действие выключает слежение до отправки команды» работает само.

- **Кто держит скорость.** Скорость геймпада помнит `GamepadBridge` (`velocity()`); клавиатура и экранный джойстик — свои. В камеру уходит сумма ±1 из `VelocityMixer` этой камеры. До четырёх геймпадов: один поток SDL (`SdlHub`, `MultiPadThread`) запускает SDL и опрашивает все (поток Qt SDL не трогает — на Mac это падение), `GamepadBridge` на геймпад, а `PadRouter` решает, какой камерой он управляет: первый геймпад — первой клеткой, Create передвигает геймпад на следующую камеру. Тачпад останавливает только камеру своего геймпада; R3 и свайп по тачпаду (крупность) действуют, только если камера геймпада выбрана в окне; L1/R1 (`SpeedStep`) — настройка самого геймпада, действует всегда (предел скорости — множитель в `GamepadBridge.velocity()`, зум не трогает) (иначе вибрация «некуда»). Деактивация окна обнуляет клавиатуру и мышь, но не геймпад; Стоп (тачпад, Esc, кнопка) и смена камеры обнуляют всех и запирают автомат (`latch_stop`) до возврата стиков и курков в центр. Намерения движения, выданные до стопа и дошедшие после него, отбрасываются по номеру поколения.
- **Обратный путь.** Цвет полосы (`PadStatus` из снимков состояния, ставится только при смене), вибрация (слежение вкл/выкл само, упор по `LimitWatch`, пресет записан, «некуда»), огоньки игрока (номер клетки камеры геймпада), заряд (`batteryChanged`). Устройство трогает только поток опроса; в него команды идут через очередь.
- **Меню Options** (`camera_menu.py`) — виджет поверх видео; для API это «открытый диалог» (409). Фокус вручную ограничен 3 с на нажатие.
- **Дальше по порядку.** Если геймпад отключили, останавливается только его камера.
- **Нет SDL / нет pygame-ce** — `SdlBackend.open()` возвращает ложь, программа работает без геймпада. SDL работает с драйвером видео `dummy`, окно не создаётся.

## Чёрный ящик (`recorder/`)

Нужен, чтобы плохой момент на площадке стал файлом, который можно разобрать и повторить без камеры.

- **Запись — только наблюдатель.** `CameraSession` создаёт `BlackBox` (или `NullRecorder`, если запись выключена). Крючки в `CommandScheduler`, `Analyzer`, `Follower`, `CameraSession` зовут `safe_event`/`safe_frame`, которые не бросают исключений и не блокируют: слежение и команды от записи не зависят.
- **Что пишется.** Кадры — 5 к/с, JPEG q70, не больше 640×360. События (`events.py`, `KINDS`): `analysis` (результат анализа), `control` (такт регулятора с входами и кодами), `cmd` (отправленная команда и ответ), `position` (`#APC`/`#GZ`), `follow` (вкл/выкл, причина, `video_latency`), `target`, `note`.
- **Буфер.** Кольцо по времени (`ring.py`), по умолчанию 5 мин. Кадры и события идут разными очередями: очередь кадров — не больше 50 полных кадров (`FRAME_QUEUE_SIZE`), при переполнении новые кадры выбрасываются; события — никогда. Строку события (`event_line`) готовит вызывающий поток. Фоновый поток кодирует и складывает; zip пишет ещё один поток, атомарно (`.part` → переименование).
- **Снимок.** F9, пункт меню «Сохранить момент», `POST /moment` или `--lab` пишут буфер в zip: `meta.json`, `events.jsonl`, `frames.jsonl`, `frames/NNNNNN.jpg`. Папка — «Записи PTZ Tracker» на рабочем столе (`record_dir`). Постоянная запись на диск (`record_to_disk`) идёт кусками по минуте.
- **Пароли.** `redact_meta` удаляет ключи `pass/pwd/secret/token` и чистит адреса `redact_url`; `event_line` проверяет каждую строку ещё раз.
- **Положение камеры.** Пока слежение включено, `Follower` опрашивает `#APC` раз в секунду (каждые 0,75 с, пока камера поворачивается и 0,5 с после) и `#GZ` каждые 0,75 с, пока едет зум и 1 с после, иначе раз в 2 с. Без слежения, но при записи, тот же поток `Follower._poll_zoom` делает это раз в 2,0 с и молчит 2,0 с после любой ручной команды (иначе опрос задержит джойстик: камера отвечает ~7 команд в секунду). Во время калибровки опрос и пульс стоят (`quiet_for_calibration` / `resume_after_calibration`; `Follower` не заменяется, `enable()` при паузе отказывает). Последний ответ `#APC` уходит и в регулятор (`FramingInput.pan_tilt`, `pan_tilt_t`): сторож раскачки (`framing.SwingWatch`) засчитывает разворот, только если камера по `#APC` правда проехала и развернулась; без ответов (запрос не прошёл, старая запись) — по одним командам. Те же ответы `#APC`/`#GZ` и отправленные коды (`on_sent` планировщика) идут в подстройку скорости (`control/speed_adapt.SpeedAdapter`, такт `Follower._tick`): она меняет поправку `Calibration.pan_scale/tilt_scale/zoom_scale`, через которую считаются коды (`Calibration.pan_code`, `zoom_code`, `pan_max_fw`). В настройки (`CameraConfig.speed_scale`) поправку пишет окно из потока Qt, не чаще раза в минуту. Такт `control` пишет это положение, чтобы повтор совпадал.
- **Чтение.** `Episode.open(zip)` отдаёт `meta`, `events(kind)` и `frames()`; повреждённые строки пропускает и считает (`bad_lines`).
- **Повтор.** `python -m ptztracker --replay файл.zip` — по умолчанию через регулятор (`replay_controller`): записанные такты заново идут через `FramingController`, коды совпадают с записанными (проверено: 0 расхождений на 675 тактах); с другой калибровкой, композицией или `effort` видно, что изменилось бы. Выводит сводку и PNG-графики (`--out`). `--mode analysis` прогоняет сохранённые кадры через детектор и `PersonTracker` и сравнивает цель «было/стало»; `--view` открывает `ReplayWindow`. Задержка видео берётся из события `follow on`.
- **Сдвиг картинки для трекера.** `Analyzer.motion` = `Follower.picture_motion` (замок слежения, зовёт поток анализа; слежение выключено — сдвига нет) → `FramingController.image_motion(t0, t1)`: (ratio зума, сдвиг x, сдвиг y) в долях кадра по моделям `CameraDynamics`. `PersonTracker` сдвигает предсказанные рамки; цель, потерянная ≤ 0,5 с назад, переходит на новый трек на своём месте (событие `target`, `how` = `adopt_place`).
- **Эпизод-тест.** `tests/data/episodes/sim_walk_30s.zip` и `tests/recorder/test_stored_episode.py`. Плохие эпизоды с площадки кладутся рядом и становятся тестами.

## Запись видео (`videorec/`) и нагрузка (`system_load.py`)

- `videorec/recorder.py` — `VideoRecorder`, один на `CameraSession`, свой поток. Живая камера — своё RTSP-подключение к `h264_1`, пакеты копируются без декодирования; поток нельзя скопировать — переход на `libx264`. Симулятор — кадры `session.frames` через `libx264`.
- `videorec/writer.py` — MP4 фрагментами (`frag_keyframe+empty_moov+default_base_moof`): файл читается после сбоя. На FAT32 — части по ключевым кадрам.
- `videorec/disk.py` — диск папки (`DiskWatch`, раз в 5 с в фоне); том по пути, поэтому вынутый диск не считается по родительскому.
- `videorec/controller.py` — `VideoController` без Qt: старт и стоп, запас места, автостоп, сводка и разовые сообщения; окно читает её по таймеру 500 мс.
- `ui/status_bar.py` — своя строка состояния: родной `showMessage` прячет виджеты слева. Вызовы `statusBar().showMessage(текст, мс, error=True)`.
- `system_load.py` — снимок CPU, GPU, RAM в фоне; GPU: PDH на Windows, `ioreg` на Mac (без доли процесса).
- Запись только читает камеру: ни команд, ни снятия флажков, ни выключения слежения.

## API для агента (`api/`, `ui/agent_panel.py`)

- **Доступ.** `ApiServer` слушает только `127.0.0.1:api_port` (8765), каждый запрос — `Authorization: Bearer <api_token из config.json>`; токен создаётся при первом запуске. Порт занят — окно работает без API. Токен в лог не попадает.
- **Чтение** (по умолчанию доступно всегда): `GET /status`, `GET /events?since=&limit=`, `GET /frame.jpg`; `POST /moment` сохраняет снимок.
- **Управление:** `POST /follow {"on": bool}`, `/target {"x","y"}`, `/composition {"key"}`, `/effort {"value"}`. `/calibrate` отвечает 501: мастер калибровки — модальное окно, его запускает оператор.
- **Оператор решает флажками панели «Агент»** (выключены по умолчанию, не сохраняются): «Разрешить управление агенту» и «Камера НЕ в эфире». Любая команда, что может двинуть камеру, требует **оба**; `/follow off` — только первый. Без разрешения — 403. Оба флажка у каждой камеры свои. Ручное действие, выключение слежения оператором (пробел, кнопка), смена камеры в клетке и раскачка снимают флажки этой камеры; Esc и аварийный стоп — у всех. Выбор другой клетки их не трогает. Запрос с `camera` берёт флажки и анализ этой камеры (нет такой — 404; камера без анализа — 409). Оператор снял «НЕ в эфире», а слежение включал агент (`WindowBackend._agent_follower`) — слежение выключается сразу; включённое оператором — остаётся.
- **Потоки.** Чтение идёт в потоках сервера и берёт только снимки состояния. Действия `WindowBackend` выполняет в потоке Qt через `QtInvoker` (ждёт до 2 с; Qt сервера не ждёт), поэтому проверка разрешения и действие не разъезжаются с пробелом и Esc. Во время калибровки и при открытом модальном диалоге — 409.
- **Не в эфире.** Решает только оператор флажком «Камера НЕ в эфире»; Tally ATEM на это не влияет (он только визуальный).

## Команды без окна (`lab.py`)

`python -m ptztracker --lab record|follow|calibrate --ip IP [--user …] [--seconds N] [--select X,Y] [--composition …] [--effort 0..1] [--out папка] [--save] --not-on-air`. Без окна, без Qt. `follow` и `calibrate` двигают камеру только с `--not-on-air` (иначе код 3, к камере не подключаемся). Пароль — из хранилища по камере из настроек или `PTZ_PASSWORD`; в аргументах и выводе его нет (`_scrub`). `--ip sim` — пробный прогон на симуляторе. Последняя строка вывода всегда `RESULT {json}`. Коды выхода: 0 — готово, 1 — ошибка, 2 — неверные аргументы, 3 — нет `--not-on-air`, 4 — в точке `--select` нет человека, 130 — Ctrl+C (у `follow`/`calibrate` — аварийный стоп).

**record не шлёт камере ни движений, ни стопов — безопасно при камере в эфире.** Его сессия создаётся с `CameraSession(..., observe_only=True)`: планировщик (`CommandScheduler(queries_only=True)`) принимает только запросы (`Priority.QUERY`: пульс, `#APC`, `#GZ`), а `emergency_stop()` и стоп в `stop()` ничего не отправляют. Стоп второго клиента остановил бы камеру, которую ведёт программа на Windows, и та бы не возобновила движение (`only_if_changed` не повторяет тот же код скорости). `follow` и `calibrate` (и окно) аварийные стопы шлют как прежде.

## Единицы и знаки (сквозные)

- **Координаты** в регуляторе — доли кадра (0…1).
- **Скорости:**
  - pan — fw/s, доли ширины кадра в секунду на текущем зуме (камера держит постоянные °/с — `he42.PAN_DEG_S`, поэтому fw/s кода растут при приближении как 1 / угол обзора);
  - tilt — fh/s, доли высоты (в коды переводится через `TILT_FROM_FH = 9/16`);
  - зум — ln(масштаба)/с.
- **Коды скорости камеры** 01–99, 50 = стоп. Pan > 50 — вправо, tilt > 50 — вверх, zoom > 50 — к теле.
- **Регулятор в «мировых» единицах:** смещение от центра, делённое на масштаб зума. Иначе наезд выглядел бы как ходьба человека.
- **Размер человека** — U, вертикаль «нос → линия плеч», не меньше 0,375 ширины плеч. Опорная точка — над серединой плеч. Наклон и поворот головы камеру не двигают.
- **`Frame.t_capture`** — момент получения кадра программой, а не съёмки. Задержку видео вычитает регулятор: `Calibration.video_latency` по типу потока.

## Инварианты безопасности (эфир)

1. Любое ручное действие (джойстик, зум, стрелки, пресет, фокус), Esc, смена камеры, остановка анализа (результат старше 0,6 с + задержка видео) или раскачка (сторож) **выключают слежение немедленно**. Стопы `#PTS5050`/`#Z50` уходят с приоритетом MANUAL, ручная команда в ту же ячейку их заменяет.
2. Аварийные стопы и стопы поворота/зума никогда не отбрасываются (`er2` повторяется, EMERGENCY и `#PTS5050`/`#Z50` не ограничены ретраями); при любой ошибке «последний подтверждённый» код ячейки забывается, пока ждёт аварийный стоп — пауза после обрывов не ставится, а повторы отвергаемого стопа пропускают пульс. Разовые команды (пресет, разовый AF) устаревают через 2 с без связи. Повтор того же кода сравнивается и с командой, которая сейчас в сети: стоп, нажатый до ответа камеры, уходит всегда.
3. Цель потеряна — камера плавно останавливается (~0,5 с) и ждёт. Слежение при этом остаётся включённым.
4. `CameraSession.stop()` не подвешивает UI: стопы ждём, только если камера на связи. Потоки, застрявшие в сети, — daemon.
5. Кнопка «СТОП КАМЕРЫ» равна Esc: выключает слежение до стопа, снимает разрешения агенту и не зависит от состояния Tally.
6. Пароли не попадают в лог, на экран, в отчёт диагностики и в записи чёрного ящика (`redact_url`, `mask`, `redact_meta`).
7. Агент по API двигает камеру только при двух флажках оператора («Разрешить управление агенту» и «Камера НЕ в эфире»); ручное действие, Esc, смена камеры, раскачка и аварийный стоп их снимают.
8. Запись не лежит на пути управления: её сбой или переполнение не задерживают команды и слежение.

## Регулятор (кратко; детали и причины — `docs/DECISIONS.md`)

`FramingController.step()` — чистая функция шага, тестируется в виртуальном времени (`tests/control/loop.py`, `channel=True` — через настоящий планировщик). По каждой оси:
- компенсация задержки по модели камеры (`CameraDynamics`: мёртвое время + инерция τ); модель идёт по **ушедшим** командам (`pt_sent`, `zoom_sent`);
- оценка человека (`person_estimator.PersonEstimator`): положение (фильтр 1€), скорость, центр и размах переминания, вес `walk` 0…1 («стоит»/«идёт») — плавный, без флагов;
- цель — смесь центра и человека по `walk`: стоит — держит середину, идёт — ведёт человека; упреждение × `walk`;
- одна гладкая кривая «ошибка → скорость» (`motion_law.speed_for_error`), предел разгона плавно растёт с отклонением;
- ускорение и рывок ограничены у движения камеры по модели разгона (`_Axis._ramp`); потолок — `Calibration.pan_max_fw` на текущем зуме;
- сторож раскачки — как прежде (`SwingWatch`, 4 настоящих разворота за 6 с);
- цель пропала у края — камера до `LOST_COAST_S` идёт в её сторону и шире.

Зум: наезд идёт вместе с поворотом, скорость плавно снижается, когда мало места до края или поворот не успевал бы; отъезд у края кадра и сразу — если поворотом человека не догнать; поворот подстраивается под наезд. `Follower` переводит скорости в коды по `Calibration` (таблица «код → fw/s» по зумам с поправкой подстройки скорости) и шлёт через планировщик: TRACKING для поворота, TRACKING_ZOOM для зума (окна чередуются, когда ждут оба).

## Тесты

- **Быстрый набор** `pytest -m "not slow"` — около минуты: протокол, планировщик, модели, регулятор в виртуальном времени, UI на offscreen-Qt.
- **`slow`** — реальное время на симуляторе: замкнутый контур, слежение, калибровка, диагностика. Полный прогон ~9 мин. Под нагрузкой эти тесты изредка нестабильны; это граничные метрики, а не логика.
- **Виртуальный стенд** `tests/control/loop.py` умеет: рассогласование скорости камеры (`speed_factor`), задержку очереди (`cmd_delay`), зум у края объектива. Новые свойства регулятора проверяются сначала им.

## Известные слабые места

- `ui/main_window.py` собирает окно (конструктор по шагам `_build_*`, Qt-события, список камер), остальное — части-примеси `ui/window_*.py` по темам: клетки, слежение, пресеты, запись, состояние, ввод, геймпады. Разделение механическое: состояние общее (`self`), части зовут друг друга напрямую. Следующий шаг, если понадобится, — вынимать настоящие объекты с данными (начать с геймпадов).
- **Угловые скорости симулятора совпадают с моделью регулятора по построению** (оба — из `he42.PAN_DEG_S`). Ошибки таблицы «код → скорость» на нём не видны, их ловит только виртуальный стенд с `speed_factor`, а саму таблицу против замеров — стенд с `cam_he42=True` и повтор записей с площадки. Геометрию (скорость в кадре растёт к краям, трапеция при наклоне, бочка, размер по глубине) проективный кадр уже показывает.
- **У конфига нет номера версии схемы.** Новые поля добавляются со значениями по умолчанию; переименование полей потребует миграции.
- **Нет проверки типов (mypy).** Регресс по типам ловят тесты; numpy-числа из ключевых точек уже однажды сломали арифметику со знаками.
