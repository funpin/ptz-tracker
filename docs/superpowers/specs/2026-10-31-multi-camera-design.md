# Несколько камер одновременно: сетка 2×2, до 4 операторов с геймпадами

Дата: 2026-10-31. Статус: черновик после проверки, ждёт одобрения пользователя.
Макет окна (вариант A) показан пользователю 2026-10-31, выбран A.

## Зачем

Сейчас программа ведёт одну камеру: в `MainWindow` одна `self.session` (`camera/session.py`), смена камеры в выпадающем списке пересоздаёт сессию. На площадках нужно больше.

- **Обычный случай (пользователь):** один оператор, одна-две камеры, обе ведёт с одного геймпада DualSense и переключается между ними с геймпада.
- **Предельный случай (пользователь):** до 4 операторов за одной программой, у каждого свой геймпад и своя камера, все видят до 4 картинок.
- Номера камер на площадках разные (где-то PTZ 2 и 3, где-то PTZ 1 и 2); в списке программы лежат камеры двух площадок, нужные выбираются на месте.

**Успех:** оператор ставит в сетку камеры этой площадки, подключает геймпады, и каждая камера управляется своим геймпадом (или одним по очереди), не мешая другим; аварийный стоп останавливает всё.

## Цели

1. До 4 камер одновременно, у каждой своя сессия: видео, планировщик команд, по желанию анализ и слежение.
2. Окно — всегда сетка 2×2 + правая панель управления выбранной камерой.
3. До 4 геймпадов; геймпад переключается между камерами кнопкой Create; несколько геймпадов могут вести одну камеру.
4. Нагрузку от нейросети ограничивает настройка.

## Не цели

- **Запись видео** (H.264 1920×1080p50 с камер, включается отдельно; пользователь хочет) — отдельная спека после этой работы. Здесь только оставляем место: в служебной клетке строка про запись, в сессии — точка, куда запись подключится.
- Регулятор, слежение, калибровка (`control/`, `framing/`) — не меняются: каждая сессия работает как сейчас одна.
- Раскладка геймпада — по спеке `2026-10-30-gamepad-dualsense-design.md`; здесь только маршрутизация и Create.
- Сетка другого размера (1×1, 3×3, «главная + мини») — нет: всегда 2×2 (пользователь).

## Анти-цели

- Оператор одной камеры случайно двигает или останавливает чужую камеру (кроме Esc, который нарочно останавливает все).
- Стоп потерялся, потому что команда ушла не в ту сессию или сессия закрылась.
- Окно подвисает из-за 4 потоков видео или опросов.
- Нейросеть на нескольких камерах грузит слабый ПК так, что OBS/vMix теряют кадры.
- Агент двигает камеру, у которой нет флажков оператора, потому что они стоят у другой камеры.

## Как устроено окно (вариант A)

```
┌ верхняя панель (как в спеке main-window-layout; без выпадающего списка камер) ──┐
├──────────────────────────────┬──────────────────────────────┬──────────────────┤
│ клетка 1: PTZ 2 ▾  🎮         │ клетка 2: PTZ 3 ▾  🎮         │ правая панель    │
│ видео, рамка Tally, TRACK    │                              │ выбранной камеры │
├──────────────────────────────┼──────────────────────────────┤ (кадр, джойстик, │
│ клетка 3: Камера: нет ▾       │ клетка 4: Камера: нет ▾       │ ирис, gain, …,   │
│ служебная информация          │ служебная информация          │ СТОП · Esc)      │
└──────────────────────────────┴──────────────────────────────┴──────────────────┘
```

### Клетки

- В левом верхнем углу клетки — имя камеры с ▾ (в пустой — «Камера: нет ▾»). Список: «нет» + камеры из настроек, **кроме уже стоящих в других клетках** (одна камера — не больше одной клетки; пользователь).
- Выбор камеры в клетке открывает её сессию; «нет» — закрывает (сначала стоп камере, как сейчас при смене камеры). Смена камеры в клетке = «смена камеры» для инвариантов этой клетки.
- Расстановка сохраняется в `config.json` и восстанавливается при запуске. *(моё решение: `AppConfig.grid: list[str | None]` из 4 id; `last_camera_id` при чтении старого конфига ставится в клетку 1; id, которого больше нет в списке камер, — клетка «нет». Запуск с `--sim` расстановку в конфиг не пишет, как сейчас не пишет `last_camera_id`.)*
- На картинке: имя и номер клетки, значки геймпадов, которые ведут камеру (🎮 на каждый геймпад), состояние TRACK и крупность, рамка Tally (красная/зелёная по `atem_input` этой камеры), экран standby/«нет видео» — как сейчас, но внутри клетки.
- **Выбранная камера** — в синей рамке. Клавиатура (стрелки, зум, Пробел, 1–5), мышь и правая панель командуют ей. Верхняя панель (Видео, Анализ, TRACK) показывает её. Клик по невыбранной клетке **только выбирает её**; следующий клик по уже выбранной — выбор человека, как сейчас. *(моё решение)*
- Кнопки «сбросить цель» и «скелет» поверх видео — в каждой клетке со своей камерой.

### Служебные клетки (пустые клетки)

*(содержание и распределение — моё решение; пользователь предложил примеры, поправим по месту)*
- Первая пустая клетка: положение каждой камеры в сетке цифрами — P (°), T (°), Z (×) — и «вид сверху»: дуга и луч направления каждой камеры её цветом/номером клетки.
- Вторая пустая: графики P/T/Z за последние 30 с для выбранной камеры; ниже — строка «Запись» (пока «запись видео — в следующей версии» или скрыта; заполнит спека записи).
- Третья (если подключена одна камера): сводка — геймпады (номер, камера, заряд, если SDL отдаёт), анализ каждой камеры (к/с, мс), связь.
- Положение берётся опросом `#APC` и `#GZ` каждой сессии с приоритетом `QUERY`, ~2 раза в секунду, **только пока видна служебная клетка с положением или графиком** (пульс в 2 с — отдельно, как сейчас). Перевод в градусы и кратность — из модели `camera/he42.py`. Если камера ведёт слежение, берём то, что уже опрашивает `Follower`, а не шлём второй запрос. *(моё решение; конкретный способ делить опрос с Follower — строителю)*

### Верхняя панель и меню

- Выпадающего списка камер нет (выбор — в клетках). Шестерёнка «Добавить / Изменить / Удалить камеру» остаётся; удалить камеру, стоящую в клетке, — сначала клетка становится «нет».
- Видео, Анализ, TRACK — выбранной камеры. ATEM — общий. Чёрный ящик: F9 сохраняет zip **по каждой открытой камере** (один F9 — до 4 файлов, имя файла с именем камеры). *(моё решение)*
- Меню ☰ → Калибровка, Диагностика, Включить/standby — для выбранной камеры; в заголовке диалога имя камеры. Диалог привязывается к сессии в момент открытия; пока он модальный, выбрать другую клетку нельзя. Если сессию закрыли (клетка «нет» по API невозможна, оператор занят диалогом) — не бывает; на всякий случай диалог закрывается при закрытии своей сессии. *(моё решение)*
- Окно ~1640×850 по-прежнему. Клетка при этом ~630×355 — 16:9 помещается.

## Остановка и ручное управление

- **Esc и кнопка «СТОП КАМЕРЫ»** — останавливают **все** камеры, выключают слежение на всех, обнуляют все удерживаемые скорости (клавиатура, мышь, все геймпады — стик нужно вернуть в центр), снимают все флажки агента. (пользователь)
- **Тачпад геймпада** — стоп только камеры этого геймпада (как `emergency_stop` одной сессии) и обнуление стиков всех геймпадов, которые её держат. *(моё решение, пользователь не возражал)*
- Ручное действие на камере X (клавиши, мышь, панель, геймпад) выключает слежение и снимает флажки агента **камеры X** до отправки команды — путь тот же, `CameraSession._manual`. Другие камеры не трогаются.
- Смена выбранной камеры (синей рамки): удерживаемые клавиши и мышь отпускаются у прежней (как сейчас `release_all_held` при смене), геймпады не затрагиваются.

## Слежение и нагрузка

Факт: на целевом ПК (GTX 1650, DirectML, рядом OBS) анализ одной камеры — 13–14 к/с (спека §7). Две камеры с анализом получат примерно половину каждая — непроверено.

- В настройках камеры (диалог камеры) — галочка **«Слежение доступно»** (`CameraConfig.tracking: bool`, по умолчанию да). Без неё у камеры нет анализа и слежения: только ручное управление; TRACK и выбор человека неактивны, подсказка объясняет.
- В общих настройках — **«Сколько камер анализировать одновременно»** (`AppConfig.max_analyzed: int`, 1…4, по умолчанию 1). (пользователь) Поднимем после замера на площадке. *(где именно в интерфейсе — моё решение: окно «Настройки…» в ☰ или рядом с настройками записи; строителю)*
- Кто получает анализ, если претендентов больше лимита *(моё решение, пользователь видел)*: сначала камеры с включённым TRACK; оставшиеся места — выбранной камере (чтобы видеть скелеты и выбрать человека), если у неё «Слежение доступно». Анализ включается/выключается на ходу при смене выбранной камеры.
- Включить TRACK на камере сверх лимита — отказ с сообщением «Уже следит PTZ 2 — выключите там или увеличьте число камер в настройках». Тихо снимать слежение с другой камеры нельзя.
- Отбирать анализ у камеры с включённым TRACK программа не может никогда.
- На камере без анализа вместо «Анализ N к/с» — «без анализа».
- Сессия получает методы `start_analysis()` / `stop_analysis()` (сейчас анализ задаётся только при создании). Остановка анализа на камере выключает её слежение **до** остановки потоков (инвариант).
- Распределение анализа — чистая функция (кандидаты, TRACK, выбранная, лимит → множество камер), тестируется без Qt.

## Геймпады

Согласовано с пользователем 2026-10-31:

- Геймпады внутри программы нумеруются 1–4 в порядке подключения (новый берёт первый свободный номер); на самом геймпаде точки показывают номер клетки его камеры (см. ниже).
- Подключённый геймпад берёт **первую по порядку клеток камеру, которую не ведёт никакой геймпад**; если все заняты — первую по порядку.
- **Create** — переключить геймпад на следующую камеру по кругу: сначала ищется следующая свободная (не занятая другим геймпадом); если свободных нет — просто следующая. Оставленная камера освобождается.
- Если геймпад переключился на камеру, которую уже ведёт другой геймпад, — **тройная вибрация** этого геймпада. (пользователь)
- Один геймпад и одна камера — Create ничего не делает (короткая вибрация «некуда»). *(моё решение)*
- Камеру убрали из клетки — её геймпады переходят по тому же правилу, как при Create; камер нет совсем — геймпад ни к чему не привязан (команды игнорируются, стики при этом ничего не шлют).
- Смена камеры геймпадом: прежней камере уходят нули от этого геймпада (стопы не теряются); новая поедет только после возврата стика в центр (как в спеке геймпада).
- Цвет полосы геймпада — состояние **его** камеры (правила спеки геймпада).
- **Несколько геймпадов на одной камере** (пользователь, вариант «сложение»): скорости поворота, наклона, зума и фокуса от всех источников камеры — каждого геймпада, клавиатуры, экранного джойстика — складываются по каждой оси с ограничением ±1. Отпустил один — второй продолжает. Пресеты, ирис, gain, разовый AF — с любого. Стоп с тачпада — для камеры, обнуляет все её источники.
- Сложение источников живёт **у каждой камеры отдельно** (а не в `MainWindow`, как в спеке геймпада): объект «смеситель скоростей» на клетку/сессию, источники — `keyboard`, `mouse`, `pad1…pad4`. Смеситель и маршрутизатор «геймпад → камера» (чистый объект: подключение, отключение, Create, закрытие клетки → привязки + какие вибрации дать) делает **эта** работа; мост геймпада из ветки геймпада вызывает их через: `camera_for_pad(n)`, `on_pad_connected(n)`, `on_pad_disconnected(n)`, `on_create(n)` и обратный канал «вибрация/цвет/точки для геймпада n». *(моё решение)*

### Белые точки под тачпадом

**Номер клетки камеры, которую геймпад сейчас ведёт** (1–4; пользователь, 2026-10-31). Меняются при Create и при переходе геймпада на другую камеру; геймпад без камеры — точки погашены. Это заменяет «номер из настройки камеры» в спеке геймпада.

На картинке камеры значки геймпадов поэтому без номеров: столько значков 🎮, сколько геймпадов её ведёт (🎮 или 🎮🎮). Внутренний номер геймпада (порядок подключения) нужен программе — для маршрутизации и в служебной клетке-сводке. *(как рисовать — строителю)*

## Агент (API)

*(моё решение)*
- Флажки хранит объект «разрешения агента» на камеру (снимок для потоков API, как сейчас `AgentPanel.control_allowed/not_on_air`), владелец — клетка; окно «Агент…» показывает их все. Старый API без `camera` — без изменений по форме ответа (добавляется только поле `cameras`).
- Оба флажка — «Разрешить управление агенту» и «Камера НЕ в эфире» — **у каждой камеры свои**: окно «Агент…» показывает строку на камеру. Обычно одна камера в эфире, а другая нет. Ручное действие, смена камеры в клетке, раскачка на камере X снимают флажки X; Esc снимает все.
- В запросы добавляется необязательный параметр `camera` (id камеры или номер клетки 1–4). Без него — выбранная камера (старые клиенты работают как раньше).
- `GET /status` — как сейчас для выбранной камеры + поле `cameras` со списком по клеткам (то же содержимое для каждой). `GET /frame.jpg?camera=…`.
- 409, пока у **этой** камеры идёт калибровка или открыт любой модальный диалог / меню Options любого геймпада на этой камере.
- `AGENTS.md` и `docs/ARCHITECTURE.md` обновить: инварианты «на камеру».

## Инварианты (каждый — на камеру)

- Ручное действие, смена камеры в клетке, остановка анализа, раскачка выключают слежение **этой** камеры до её следующей команды. Esc — всех.
- Стопы не теряются ни при смене камеры у геймпада, ни при закрытии клетки, ни при закрытии окна (у каждой сессии свой `CommandScheduler`).
- Поток Qt не ждёт сеть: закрытие сессии — как сейчас (`stop()` не ждёт зависших потоков); 4 сессии закрываются без суммирования ожиданий. *(строителю: параллельно, общий потолок ~1,5 с при выходе)*
- Пароли не попадают в логи/подсказки/записи.
- Запись чёрного ящика — у каждой сессии своя, только наблюдает.

## Симулятор и тесты

- `--sim` добавляет 4 камеры-симулятора («Симулятор 1»…«4», у каждой свой `SimHttpServer` на своём порту); при первом запуске с `--sim` в сетке — «Симулятор 1» и «Симулятор 2». *(моё решение)*
- Тесты на нескольких симуляторах одновременно: независимость команд (геймпад 1 двигает только свою), стоп одной камеры не трогает другую, Esc останавливает все, сложение двух «геймпадов» на одной камере, Create с тройной вибрацией, распределение анализа по лимиту, флажки агента по камерам, закрытие клетки шлёт стоп.
- Геймпад в тестах — подставные намерения (как в спеке геймпада); живого DualSense у агента нет.

## Зависимости и порядок

- Редизайн окна (`main-window-layout`) уже в main: эта работа строится поверх него, раскладку правой панели не меняет.
- Ветка геймпада `claude/jolly-dirac-91ff96` ещё не в main. Она обещала одну функцию «камера этого геймпада» — её и заменяем. Порядок *(моё решение)*: сначала слить ветку геймпада (или её часть до `GamepadBridge`), затем эта работа; если она к тому моменту не готова — делаем маршрутизацию и смеситель с подставными намерениями, мост подключится позже. Смеситель скоростей из спеки геймпада переезжает «на камеру» — договориться с той веткой, чтобы не делать его дважды.
- Запись видео — следующая спека.

## Ограничения

- Python 3.12–3.13, PySide6; сборка Windows; живая камера и геймпад с машины разработчика недоступны.
- 4 потока видео: на площадке с 4 камерами разумно MJPEG 640×360 для картинок; H.264 1080p50 ×4 — проверить на целевом ПК (в BACKLOG).

## Решения пользователя

- Сетка 2×2 всегда + правая панель для выбранной камеры (вариант A).
- В пустых клетках — служебная информация (положение, графики, запись).
- Любая камера — в любую клетку, но только один раз; в выборе есть «нет».
- Слежение по умолчанию — не больше 1 камеры; галочка «Слежение доступно» на камере; число одновременно анализируемых камер — настройка.
- Esc / «СТОП КАМЕРЫ» — все камеры.
- Геймпады: по порядку подключения, первая свободная камера, Create — следующая (свободная, а если нет — любая), тройная вибрация при попадании на занятую.
- Несколько геймпадов на одной камере — скорости складываются.
- Белые точки на геймпаде — номер клетки камеры, которую он ведёт.
- Запись видео — отдельно, после.

## Решения, принятые мной (проверьте)

- Первый клик по невыбранной клетке только выбирает её.
- Флажки агента — у каждой камеры свои; параметр `camera` в API, без него — выбранная.
- F9 сохраняет записи всех открытых камер.
- Распределение анализа: TRACK → выбранная; отказ сверх лимита без отбора у других.
- Тачпад — стоп только своей камеры.
- Опрос положения ~2 Гц только при видимой служебной клетке.
- `--sim` даёт 4 симулятора, в сетке два.
- Порядок: сначала геймпад в main, потом эта работа.
