# PTZ Tracker — дизайн

Дата: 2026-10-19
Статус: черновик на одобрение

## 1. Зачем это

На мероприятиях работают 1–2 человека, у которых несколько камер и трансляция. Если оператор вручную ведёт докладчика, он полностью занят этим и не может заниматься остальным. Программа должна снять с него эту работу: камера Panasonic AW-HE42 сама плавно держит выбранного человека в заданной композиции, а оператор только выбирает, кого вести и как, и в любой момент может перехватить управление.

Камера должна двигаться «как человек»: не дёргаться от покачиваний, мягко трогаться и тормозить, не перелетать цель и не терять её.

## 2. Цели, не-цели, анти-цели

**Цели (v1)**
- Управление одной камерой AW-HE42 по IP: ручное (поворот, зум, фокус, ирис/яркость, пресеты) и автоматическое слежение.
- Оператор кликает по человеку на превью, и программа ведёт именно его.
- Композиции: по пояс (центр / слева / справа), в полный рост, общий план, своя зона, нарисованная мышкой и сохранённая как пресет.
- Плавность движения, настраиваемая «усилием» (Мягко ↔ Резко).
- Выбор метода слежения: нейросеть, классический трекер, гибрид.
- Список камер (имя + IP) с запоминанием; настройки отдельно для каждой камеры.
- Запуск на Windows 10 22H2 как обычная программа (.exe), без установки Python.

**Не-цели v1** (держим в голове, архитектура их не должна блокировать)
- Одновременное слежение несколькими камерами и их координация.
- Режимы для концертов и танцев: быстрые движения, слежение за группой.
- Другие модели камер и протоколы (VISCA, NDI-управление).

**Анти-цели** (даже если «работает», это провал)
- Камера дёргается, рыскает туда-сюда или раскачивается вокруг цели.
- Камера без предупреждения перескакивает на другого человека.
- Программа мешает трансляции: грузит GPU или CPU так, что vMix или OBS начинают терять кадры.
- Оператор не может мгновенно забрать управление.

## 3. Ограничения и среда

- ПК: Core i5-10400F, GTX 1650 (4 ГБ), 8 ГБ RAM (возможно расширение до 16). Параллельно работает vMix или OBS: трансляция и запись, вход SDI с ATEM PGM.
- Видео для анализа берётся с камеры **по Ethernet** (RTSP H.264). SDI-вход ПК не трогаем.
- Камера: AW-HE42, по умолчанию `10.0.0.12`. Камер несколько, IP вводится вручную и запоминается.
- Разработка ведётся на macOS, целевая платформа Windows. **С Mac разработчика доступа к камерам нет.** Поэтому всё отлаживается на симуляторе (§12). Проверки на живой камере проводит пользователь на площадке с помощью встроенной диагностики, которая формирует отчёт для разработчика.
- **Камерой параллельно управляет аппаратный пульт** (AW-RP). Программа должна уживаться с ним (§9).

## 4. Что решил пользователь

- Основной сценарий: доклад на сцене, спикер стоит за кафедрой и/или ходит. Концерты и танцы позже.
- Сначала одна камера; несколько камер только закладываются в архитектуру.
- Цель выбирается кликом оператора по человеку на превью.
- Нужны все 6 композиций с макета: пояс центр, пояс слева, пояс справа, рост, общий, своя зона.
- Метод слежения выбирается: нейросеть / детерминированный трекер / гибрид.
- Язык и стек должны работать быстро на этом железе; конкретный выбор отдан разработчику (см. §5).
- Поведение при потере цели и при ручном вмешательстве описано в §9 и одобрено.
- Главное окно примерно как на макете: превью слева, панель управления справа, строка статуса.

Смысл композиций (решение разработчика, по макету):
- **Все композиции, включая «Общий план», следуют за человеком.** Это положение и крупность человека *в кадре*, а не фиксированная точка сцены. Фиксированные ракурсы делаются пресетами камеры.
- **«Своя зона».** Нарисованная рамка задаёт, где в кадре должен находиться человек (его тело от головы до нижней границы крупности) и какого он размера. Мёртвая и мягкая зоны строятся вокруг неё автоматически, их размер зависит от профиля усилия.

## 5. Технологии (выбор разработчика)

| Язык | Python 3.12 | Тяжёлая работа (декодирование, нейросеть) идёт в нативных библиотеках, логика работает на ~15 Гц. Лучшая экосистема CV, можно тестировать на Mac. |
| Интерфейс | PySide6 (Qt 6) | Нативное оконное приложение, превью через OpenGL/QImage, горячие клавиши. |

| Нейросеть | ONNX Runtime + **DirectML** на Windows (CPU/CoreML на Mac) | DirectML работает на GTX 1650 без установки CUDA и весит в разы меньше, чем CUDA-сборка. |
| Модель | Поза-модель класса «nano» (по умолчанию YOLO11n-pose / YOLOv8n-pose в ONNX), вход 640 | Ключевые точки (голова, плечи, бёдра) нужны для точного кадрирования «по пояс». Лицензия: см. §14. |
| Трекинг ID | ByteTrack (собственная компактная реализация) + признак внешности (HSV-гистограмма торса; опционально лёгкая Re-ID-сеть) | Удерживает «того самого» человека, когда рядом проходят другие. |

| Управление камерой | HTTP CGI Panasonic (`aw_ptz` / `aw_cam`) через `httpx` | Официальный протокол камеры. |

## 6. Архитектура

На каждую камеру создаётся свой **CameraSession**. Так несколько камер в будущем будут просто несколькими сессиями.

```
RTSP ──► VideoSource ──► (последний кадр + время захвата)
                              │
                              ├──► Preview (UI, 25 fps)
                              └──► Analyzer (~10–20 Гц) ──► Detections/Track (цель, ключевые точки)
                                                                  │
                    CompositionPreset ──────────────────────────► FramingController
                    EffortProfile ───────────────────────────────►   (оценка, регулятор, профиль скорости)
                    CameraModel (калибровка) ────────────────────►        │
                                                                          ▼
                                    ManualInput ──► Arbiter ──► CommandScheduler ──► Camera HTTP
                                                                          ▲
                                                           CameraStateEstimator (положение, зум)
```

Модули (каждый тестируется отдельно):
- `camera/protocol` — сборка и разбор команд Panasonic, HTTP-клиент, авторизация.
- `camera/scheduler` — очередь команд: минимальный интервал между командами, приоритеты, **склейка** (новая `#PTS` заменяет ещё не отправленную старую), отправка только при изменении значения.
- `camera/state` — оценка текущих pan/tilt/zoom: интегрирование отправленных скоростей плюс периодические запросы положения для коррекции.
- `camera/calibration` — таблицы «код скорости → °/с» и «позиция зума → угол обзора».
- `video/source` — RTSP-приём, низкая задержка, переподключение.
- `vision/detectors` — общий интерфейс `Detector`; реализации `PoseDetector` (ONNX), `ClassicTracker` (CSRT/KCF), `Hybrid`.
- `vision/tracking` — ByteTrack + признаки внешности, логика «выбранной цели».
- `framing/composition` — пресеты и пользовательские зоны.
- `framing/controller` — регулятор (§8).
- `framing/supervisor` — машина состояний: слежение, потеря, поиск, ручной режим (§9).
- `ui/` — окна и виджеты.
- `config/` — хранение настроек.
- `sim/` — виртуальная PTZ-камера для разработки и тестов (§12).

## 7. Камера: протокол AW-HE42

Источник: Panasonic «HD Integrated Camera Interface Specifications» (семейство AW-HE/UE). Формат и ограничения у моделей семейства общие. **Каждый пункт с пометкой ⚠ нужно проверить на живой HE42 в начале реализации.**

- Формат: `http://<IP>/cgi-bin/aw_ptz?cmd=%23<КОМАНДА>&res=1`, ответ `200 OK` с телом-эхом (например, `pTS5050`). Команды `#…` идут в `aw_ptz`, команды камеры (OSD/изображение) в `aw_cam`.
- **Между командами нужен интервал не меньше 130 мс.** Keep-Alive не поддерживается, каждый запрос открывает новое соединение. Команды, меняющие состояние, шлются только при изменении значения, а не по таймеру.
- Pan/tilt по скорости: `#PTS<pan><tilt>`, коды `01–99`, `50` означает стоп; `01` максимум влево/вниз, `99` максимум вправо/вверх. Получается 49 ступеней в каждую сторону, шкала нелинейная, поэтому нужна калибровка.
- Pan/tilt абсолютно: `#APC<pan4hex><tilt4hex>`, центр `80008000`. ⚠ Как запросить текущее положение (`#APC` без данных или другая команда).
- Зум по скорости: `#Z01–99` (`50` стоп, `<50` к широкому углу, `>50` к теле). Абсолютно: `#AXZ555–FFF`. Запрос: `#GZ`. ⚠
- Фокус: автофокус вкл/выкл `#D1x`, скорость `#Fxx`, абсолютно `#AXF`, разовый AF ⚠.
- Ирис и яркость: авто-ирис `#D3x`, позиция `#AXI`/`#Ixx`; усиление и экспозиция через `aw_cam` ⚠.
- Пресеты: вызов `#Rxx`, запись `#Mxx`.
- ⚠ Авторизация (Digest/Basic), если она включена в веб-настройках камеры.
- ⚠ Настройка камеры «Speed With Zoom Pos.»: при ON камера сама замедляет pan на теле. Калибровка учитывает любое значение, но рекомендуемое значение выберем по результатам теста.

Следствие для плавности: пока камера едет, оператор-программа может отправлять примерно 7 команд в секунду **на все команды вместе** (pan/tilt и зум делят этот бюджет). Поэтому плавность достигается не частотой команд, а тем, *какие* скорости и *когда* отправлять (§8). Планировщик даёт `#PTS` приоритет над `#Z`. Если на живой камере выяснится, что интервал можно сократить, это настраиваемый параметр.

## 8. Регулятор движения: «как оператор»

**Входы:** положение и размер цели в кадре (нормализованные координаты) с меткой времени кадра, текущая композиция, профиль усилия, калибровка камеры.

**Шаги на каждом такте:**
1. **Компенсация задержки.** Кадр из RTSP устарел на L (~0,2–0,5 с, измеряется). Мы знаем, какие скорости отправляли за это время, поэтому пересчитываем положение цели на «сейчас».
2. **Оценка движения цели.** Фильтр Калмана (постоянная скорость) в угловых координатах сцены: угол камеры + смещение в кадре × угол обзора. Получаем угловую скорость человека, это упреждение.
3. **Ошибка композиции.** Разница между фактической точкой привязки (по ключевым точкам: например, середина плеч для «по пояс») и желаемой точкой пресета.
4. **Зоны.**
   - Внутри мёртвой зоны ошибка считается нулевой.
   - В мягкой зоне усиление растёт плавно.
   - У края кадра включается усиленный режим, чтобы не упустить человека.
   - Есть гистерезис: камера трогается при выходе за зону, а останавливается, когда человек возвращается ближе к центру зоны. Так нет «дребезга» на границе.
5. **Желаемая скорость** = упреждение (скорость человека) + коэффициент × ошибка. Регулятор критически демпфирован, без перелёта.
6. **«Место для взгляда».** Когда человек идёт, точка привязки смещается против направления движения, и перед ним остаётся больше места, как делает живой оператор. Смещение пропорционально скорости и плавно возвращается назад, когда человек останавливается.
7. **Профиль скорости.** Ограничения на скорость, ускорение и рывок (S-кривая), без ступенек.
8. **Перевод в коды скорости** через калибровочную таблицу, с учётом текущего зума: на теле скорость меньше. Между соседними кодами работает гистерезис, чтобы не скакать 53↔54. Команда уходит, только если код изменился.

**Зум** работает по своему контуру:
- Ошибка = log(желаемый размер / фактический размер); размер берётся по ключевым точкам, например голова–бёдра для «по пояс».
- Мёртвая зона по размеру шире, скорость зума ниже.
- Наезд (приближение) разрешён только при уверенном трекинге и малой скорости поворота.
- Отъезд выполняется сразу, если человек подходит к краю кадра.

**Профиль усилия** — это набор параметров с тремя заводскими точками (Мягко / Обычно / Резко) и ползунком между ними: максимальная скорость pan/tilt и зума, ускорение, рывок, размеры мёртвой и мягкой зон, порог реакции. Точные числа подбираются на симуляторе и на живой камере.

**Калибровка** запускается мастером из UI и занимает около 1–2 минут. Камера проходит набор кодов скорости при нескольких положениях зума. Сдвиг картинки меряется фазовой корреляцией или оптическим потоком, и строятся таблицы «код → °/с» и «зум → угол обзора». Результат сохраняется для каждой камеры. Пока калибровки нет, работает разумная таблица по умолчанию.

## 9. Состояния слежения

- **Ожидание:** слежение выключено, оператор кликает по человеку, и цель выбрана.
- **Слежение:** работает регулятор.
- **Кратковременная потеря** (до ~2 с, настраивается): камера плавно останавливается и держит позицию, трекер ищет цель в окрестности.
- **Поиск:** камера плавно отъезжает на более общий план. Цель принимается обратно только при совпадении по внешности с выбранным человеком. Нашлась — плавный возврат к композиции.
- **Потеряна** (после N с поиска, настраивается): камера уходит на заданный пресет, например общий план сцены. На экране крупно горит «ЦЕЛЬ ПОТЕРЯНА». Повторный выбор цели делается кликом.
- **Ручной перехват:** любое ручное действие (джойстик, зум, пресет) мгновенно ставит слежение на паузу, и ручные команды получают приоритет в планировщике. Через настраиваемую паузу после отпускания слежение продолжается с текущего положения; можно также настроить, чтобы оно оставалось выключенным до нажатия кнопки.
- **Пульт и другое внешнее управление.** Камерой параллельно управляет пульт AW-RP; кроме него могут вмешаться PTZ-панель vMix или веб-интерфейс. Как программа это замечает:
  1. Подписывается на **уведомления камеры об изменениях** (update notifications, TCP-приёмник на стороне ПК; камера поддерживает до 5 получателей, пульт занимает одного) ⚠.
  2. Если уведомления не сообщают о движениях с пульта, программа периодически запрашивает положение и зум в свободных окнах планировщика и сравнивает с оценкой.
  3. Расхождение больше порога или уведомление о команде не от программы считается внешним перехватом: слежение уходит в паузу, как при ручном вмешательстве, и в статусе горит «ПУЛЬТ».
  4. Возобновление настраивается: через паузу после последнего движения пульта или только по кнопке. По умолчанию — по кнопке, чтобы не бороться с оператором пульта.

  Пульт и программа делят общий лимит команд камеры. Пока слежение включено, оператор пульта эту камеру не трогает, это правило эксплуатации.
- **Аварийный стоп:** отдельная клавиша мгновенно шлёт `#PTS5050` и `#Z50`.

## 10. Интерфейс

- Главное окно, как на макете:
  - **Слева:** превью с рамками людей. Выбранная цель выделена, остальные кликабельны. Поверх кадра рисуются мёртвая и мягкая зоны текущей композиции и сетка третей.
  - **Справа:**
    - выбор камеры (выпадающий список и «+ добавить»);
    - большая кнопка «СЛЕЖЕНИЕ ВКЛ/ВЫКЛ»;
    - кнопки композиций;
    - ползунок «Мягко ↔ Резко»;
    - выбор метода;
    - ручное управление: экранный джойстик мышью, зум, фокус (AF, разовый AF, ближе/дальше), ирис/яркость, вызов и запись пресетов камеры.
  - **Снизу:** статус — подключение, fps потока и анализа, задержка, загрузка GPU и CPU, предупреждения.
- «Своя зона»: оператор тянет рамку на превью, задаёт имя, и пресет сохраняется.
- Горячие клавиши: пробел включает и выключает слежение, 1–9 переключают композиции, Esc — аварийный стоп, стрелки и +/− управляют вручную.
- Диалог камер: имя, IP, логин и пароль (если нужны), RTSP-адрес (по умолчанию подставляется автоматически, но его можно переопределить), кнопка «Проверить связь».
- Язык интерфейса русский.

## 11. Хранение настроек

`%APPDATA%\PTZTracker\config.json` на Windows (на Mac аналогичный путь в профиле). Что хранится:
- список камер;
- для каждой камеры: последняя композиция, профиль усилия, метод, калибровка, пользовательские зоны, параметры потери цели;
- глобальные настройки: горячие клавиши, размер окна.

Пароли хранятся в Windows Credential Manager через `keyring`, а не в JSON открытым текстом.

## 12. Разработка и проверка без камеры

- **Виртуальная PTZ-камера (`sim/`).** Берёт видео высокого разрешения с общим планом сцены (запись доклада) и «снимает» его движущимся окном. Окно двигается по тем же командам `#PTS`/`#Z` с инерцией камеры, нелинейной таблицей скоростей и искусственной задержкой потока. Ещё есть поддельный HTTP-сервер `aw_ptz` и выдача видео как RTSP или как локальный источник. Вся программа работает против симулятора так же, как против живой камеры.
- **Модульные тесты:** протокол (сборка и разбор), планировщик (интервалы, склейка, приоритеты), математика композиций, регулятор на синтетических траекториях (нет перелёта, нет дребезга, ограничения рывка соблюдены), машина состояний.
- **Метрики плавности** на симуляторе: максимальный рывок, число смен направления, число отправленных команд, время удержания цели в зоне.
- **Проверка на живой HE42.** Разработчик к камере доступа не имеет, поэтому в программу (и отдельным режимом `.exe --diagnose`) встроена **«Диагностика камеры»**. Пользователь запускает её на Windows-ПК в сети камер. Она автоматически проверяет:
  - связь и авторизацию;
  - RTSP-адреса (перебирает известные варианты) и измеряет задержку потока;
  - команды из §7 (⚠), их ответы и реальный минимальный интервал;
  - запрос положения и зума;
  - приходят ли уведомления, в том числе о движениях с пульта;
  - короткий прогон калибровки.

  Результат — архив с отчётом и логами, который пользователь присылает разработчику. Камера при этом делает только небольшие движения и возвращается в исходное положение.
- **Видео для симулятора.** Нужна запись доклада общим планом в максимальном разрешении. Пока её нет, используются открытые записи выступлений и синтетические сцены.

## 13. Этапы

1. **Каркас, связь и диагностика:** проект, конфиг, список камер, RTSP-превью, ручное управление, симулятор камеры (HTTP + видео), «Диагностика камеры». Сборка `.exe`, чтобы пользователь как можно раньше прогнал диагностику на площадке. По её отчёту закрываются ⚠-пункты протокола.
2. **Видение:** нейросетевой детектор, трекинг, клик по человеку, рамки на превью, замер нагрузки на GTX 1650 рядом с vMix/OBS.
3. **Регулятор:** симулятор, композиции, зоны, профиль усилия, калибровка.
4. **Поведение:** потеря и поиск цели, ручной перехват, горячие клавиши, классический и гибридный методы, «своя зона».
5. **Сборка и площадка:** `.exe` для Windows, прогон на реальном мероприятии, донастройка профилей.

## 14. Открытые вопросы

- **Лицензия модели.** Модели Ultralytics YOLO распространяются под AGPL-3.0. *По умолчанию (решение разработчика, ответа пока нет) программа считается внутренней*, поэтому берём YOLO-pose. Если её когда-нибудь будут передавать или продавать, модель меняется на Apache-2.0 (RTMO или RTMDet + RTMPose). Детектор спрятан за интерфейсом, так что меняется только файл модели и её постобработка.
- **Сроки.** *Даты первого мероприятия нет (ответа нет)*, поэтому этапы идут по порядку. Если дата появится, первыми откладываются классический и гибридный методы и мастер калибровки.
- ⚠-пункты протокола в §7 проверяются на живой камере на этапе 1.
