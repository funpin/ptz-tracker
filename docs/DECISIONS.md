# Решения и их причины

Каждое решение подтверждено замером или тестом. Прежде чем менять какое-то из них, воспроизведите исходную проблему тестом: значения кажутся произвольными, но за каждым стоит конкретный сбой.

## Камера и видео

| Решение | Почему |
|---|---|
| Видео для слежения — **MJPEG** `http://IP/cgi-bin/mjpeg?resolution=640x360&framerate=25`; в «Авто» он первый | Живая HE42: «команда → движение в кадре» 344 мс у MJPEG против ~830 мс у H.264 (stream_1 и stream_2): буфер декодера H.264 добавляет ~0,5 с |
| RTSP-адрес H.264 — `/MediaInput/h264/stream_1` (и `stream_2`) | `/MediaInput/h264` и `/MediaInput/stream_1` отвечают 5XX. Режим камеры «Internet mode (over HTTP)» должен быть выключен |
| Интервал команд по умолчанию 130 мс, параметр в настройках камеры | Так в спецификации Panasonic. Запросы `#O` проходили и при 50 мс, команды движения на таком темпе не проверены |
| Перехват пультом определяется опросом `#APC`/`#GZ` | Уведомления камеры (`cgi-bin/event?connect=start`) регистрируются (HTTP 204), но не пришло ни одного; опрос раз в 0,7 с видит движения пульта надёжно |
| Замеры HE42 живут в `camera/he42.py` и больше нигде | Симулятор и модель регулятора однажды разошлись в 1,7 раза: проверка слежения на симуляторе обманывала |

## Планировщик команд

| Решение | Почему |
|---|---|
| Склейка по ключу (`pt`, `zoom`, …) + «только если изменилось» + возврат к отправленному значению отменяет ожидающую команду | Камера принимает ~7 команд/с; оператор и регулятор шлют намного чаще |
| `er2` (занята, например пультом) и EMERGENCY повторяются до успеха; `er1`/`er3` — не больше 3 раз | Стоп, отброшенный после трёх «занята», оставлял камеру в движении в эфире |
| Разовые команды (пресет, разовый AF) живут 2 с | Пресет, нажатый при обрыве связи, срабатывал минуты спустя |
| Приоритеты: EMERGENCY > MANUAL > TRACKING (pt) > TRACKING_ZOOM > QUERY | Задержка поворота из-за зума — неучтённая задержка в контуре регулятора, она раскачивает его |
| Стопы при выключении слежения — с приоритетом MANUAL | Иначе стоп уходил после `#R` и мог прервать вызов пресета |

## Распознавание и цель

| Решение | Почему |
|---|---|
| Детектор отдаёт всё от 0,10; новый трек — от 0,25 (по образцу ByteTrack) | На реальном общем плане докладчик за кафедрой даёт 0,29; на рабочей крупности — 0,89 |
| Цель сопоставляется **первой**. Одиночного кандидата отвергаем, только если внешность явно чужая (> 0,6); внешность решает лишь между несколькими кандидатами | Расстояние по одежде у одного и того же человека скачет 0,12–0,37 (MJPEG 640×360, тёмная сцена). Строгий порог 0,35 рождал «двойника», который навсегда перехватывал цель (135 потерь из 149 кадров) |
| Узнанная после пропажи цель сохраняет свой номер | Оператор видел «№3 → №25» |
| Гистограммы считаются вне замка трекера, только по прямоугольнику торса | Толпа зрителей подвешивала окно на 100+ мс |
| Анализ берёт 640×360 | На рабочей крупности результат тот же, что на 1280×720 |
| ONNX Runtime: DirectML, при сбое (в том числе при первом прогоне) — CPU; 3 потока, без busy-wait | Рядом работают vMix/OBS. На целевом ПК: 13–14 анализов/с, ~31 мс, DirectML |

## Регулятор слежения

| Решение | Почему |
|---|---|
| Компенсация задержки по модели камеры: мёртвое время 0,08 с + инерция τ 0,37 с | Разгон живой камеры до 90% ~0,85 с; кадр опаздывает |
| `CameraDynamics.position(t)`, а не `displacement(0, t)` | После 10 с старые команды сворачиваются, и «смещение с момента 0» прыгало → на теле камера уезжала от человека |
| Мировые координаты делятся на масштаб зума | Иначе наезд выглядит как ходьба, и наезд идёт «ступеньками» |
| Скорость человека — наклон за 0,4 с; вес упреждения **0,5** | Регулятор устойчив, если камера в 0,5–1,7 раза быстрее модели, при задержке очереди до 0,13 с. С весом 1,0 при рассогласовании ×2 раскачивается, а на симуляторе ведёт даже хуже |
| Трогаемся, только когда человек вышел из мёртвой зоны; «пошёл» — смещение за 1,5 с | Покачивание у кафедры ±3% кадра раскачивало камеру |
| После перелёта назад — не быстрее 0,06 кадра/с, пока человек в мягкой зоне | Тормозной путь камеры ≈ v·0,6 с — перелёт неизбежен; дёргать обратно — «пинг-понг» |
| Сторож: 3 разворота с ошибкой > 0,6 мягкой зоны за 6 с → стоп и «Сервис → Калибровка» | На эфире раскачка хуже остановки. При рассогласовании ≥ ×2 надёжно срабатывает |
| Без калибровки таблица скоростей ×1,5 («камера быстрее») | Ошибиться в медленную сторону безопасно (устойчиво до ρ≈0,5), в быструю — раскачка |
| Наезд — когда человек стоит ≥ 1 с; отъезд — сразу у края; поворот компенсирует наезд; у упоров объектива зум не командуется | Плавный наезд одним движением, без «ступенек»; модель зума не «уезжает» за упор |
| Опорная точка — над серединой плеч; размер U = max(нос→плечи, 0,375·ширина плеч) | Наклон и поворот головы (взгляд в записи или на экран) двигали и зумировали камеру |
| Мастер калибровки: скорости на широком, рабочем, промежуточном зумах и на теле; разгон до 2,5 с / 90% кадра; «плоские» зумы отбрасываются | Короткие пробеги занижали быстрые коды на ~18%; без теле регулятор экстраполировал |

## Симулятор и тесты

| Решение | Почему |
|---|---|
| Симулятор отдаёт `t_capture` = момент получения (отрисовка + задержка) | Как у живой камеры; иначе задержка вычиталась дважды |
| Скорости симулятора = `he42.PAN_FW_S` × угол обзора на широком угле | Тогда в долях кадра скорость совпадает с моделью на любом зуме |
| Критерии тестов поведения — по замерам: человек в кадре, обратный ход ≤ 0,06, развороты, ускорение ≤ 2,5·a_max (а не «скачок кода») | «Перелёт ≤ 2,5% кадра» физически невозможен для этой камеры; коды скорости нелинейны |
| Тесты замкнутого контура — на откалиброванной камере плюс отдельный тест без калибровки | Штатный режим — после мастера калибровки |
