# Решения и их причины

Каждое решение подтверждено замером или тестом. Прежде чем менять какое-то из них, воспроизведите исходную проблему тестом: значения кажутся произвольными, но за каждым стоит конкретный сбой.

## Камера и видео

| Решение | Почему |
|---|---|
| Видео для слежения — **MJPEG** `http://IP/cgi-bin/mjpeg?resolution=640x360&framerate=25`; в «Авто» он первый | Живая HE42: «команда → движение в кадре» 344 мс у MJPEG против ~830 мс у H.264 (stream_1 и stream_2): буфер декодера H.264 добавляет ~0,5 с |
| RTSP-адрес H.264 — `/MediaInput/h264/stream_1` (и `stream_2`) | `/MediaInput/h264` и `/MediaInput/stream_1` отвечают 5XX. Режим камеры «Internet mode (over HTTP)» должен быть выключен |
| Интервал команд по умолчанию 130 мс, параметр в настройках камеры | Так в спецификации Panasonic. Запросы `#O` проходили и при 50 мс, команды движения на таком темпе не проверены |
| Перехват пультом определяется опросом `#APC`/`#GZ` | Уведомления камеры (`cgi-bin/event?connect=start`) регистрируются (HTTP 204), но не пришло ни одного; опрос раз в 0,7 с видит движения пульта надёжно |
| Замеры HE42 живут в `camera/he42.py` и больше нигде | Симулятор и модель регулятора однажды разошлись в 1,7 раза: проверка слежения на симуляторе обманывала |
| `he42.APC_DEG_PER_UNIT` = 0,0083 (было 0,0075 — значение симулятора) | Площадка 2026-10-29: шаги ±256/±512 ед. дали 0,0082–0,0086°/ед. по pan и tilt; документ Panasonic — 0,00824 |
| `he42.VIDEO_LATENCY_S["mjpeg_2"]` = 0,26 с (было 0,16 — оценка) | Площадка 2026-10-29: «команда → движение» 480 мс у 1280×720 12 к/с против 336 мс у 640×360 25 к/с |
| Модель камеры (`CameraConfig.model`, `firmware`) определяет сессия запросом `QID` при подключении (очередь запросов, Qt не ждёт; не ответила — повтор раз в ~10 с, `ER1`/`ER3` — больше не спрашиваем); профиль — `camera/models.py` (`profile_for`): HE42 и HE40, неизвестная или ещё не определённая модель берёт HE42 и пишет предупреждение в журнал один раз. В профиле только замеры: замедление поворота на теле (одна таблица `he42.TELE_PAN_DEG_S` для обеих), `image_controls_verified` (HE40 — да, HE42 — нет), интервал команд 0,130 с (как в `CameraConfig`); «HE40 на кодах 70–90 быстрее на 2–17%» — справка (`speed_note`), таблица скоростей одна, расхождение ловит подстройка | Пробы 2026-10-29 (HE42) и 2026-10-30 (HE40, §7): таблица и τ совпали в пределах 0–3% на 53–67, на 70–90 HE40 быстрее — это уже покрывает `speed_adapt`. Запроса прошивки в известном нам протоколе нет — `firmware` остаётся из настроек (калибровка 3 пишет её, если узнает). Уточнено 2026-11-06: HE40 отвечает на `QSV` (`OSV:Ver.1.82`, §7 спеки) — подключить в сессию отдельной задачей (BACKLOG). Тесты `tests/camera/test_models.py`, `test_session.py` |
| Возможность, на которую камера ответила `ER1` (gain `QGU`/`OGU`, баланс белого `QAW`/`OAW`, цветовая температура `QSD:B1`/`OSD:B1`, питание `#O`), запоминается в `CameraConfig.unsupported` и виден в `CameraSession.camera_info()`; успешный ответ на ту же возможность пометку снимает, смена модели — сбрасывает. `ER2`/`ER3` ничего не помечают | `ER1` — «команды нет» (HE40 так отвечает на `QBV`, `QSI:20` и др., §7); `ER2` — занята или ожидание, `ER3` — значение вне диапазона, это не отсутствие возможности. Сессия настройки не меняет (поток планировщика), окно сохраняет само. Тесты `tests/camera/test_session.py` |

## Планировщик команд

| Решение | Почему |
|---|---|
| Склейка по ключу (`pt`, `zoom`, …) + «только если изменилось» + возврат к отправленному значению отменяет ожидающую команду | Камера принимает ~7 команд/с; оператор и регулятор шлют намного чаще |
| `er2` (занята, например пультом) и EMERGENCY повторяются до успеха; `er1`/`er3` — не больше 3 раз, но стопы поворота и зума (`#PTS5050`, `#Z50`) и аварийные по счётчику не отбрасываются никогда (2026-11-07). При любой ошибке программа забывает «последний подтверждённый» код ячейки (исход неизвестен — повтор стопа не считается дублем), пока ждёт аварийный стоп, пауза после обрывов не ставится, а повторы отвергаемого стопа пропускают пульс (`probe_key`); одинаковое предупреждение о сбое пишется в журнал не чаще раза в 5 с | Стоп, отброшенный после трёх «занята», оставлял камеру в движении в эфире. Анализ 2026-11-07: потерянный стоп (дубль команды в пути, таймаут без забытого `last_sent`, пауза перед Esc) и журнал, прокручивавшийся за 1,5–2 часа повторами при обрыве. Тесты: `tests/camera/test_scheduler.py` |
| Мастер калибровки и диагностика (`diagnostics/probe.py` `Pacer`) повторяют команду на er2 через 0,15 с (`ER2_RETRY_S`), не дольше 2 с (`ER2_RETRY_TOTAL_S`), потом бросают ошибку; er1/er3 не повторяются. Было: первая же er2 прерывала калибровку | Они шлют мимо планировщика, а камера (и симулятор) отвечают er2 на команды чаще ~130 мс: под нагрузкой `test_lab_calibrate_sim_prints_json` падал. Камера в ожидании отвечает ER2 на всё — через 2 с ошибка, а не зависание. Тесты: `tests/diagnostics/test_pacer.py` |
| Разовые команды (пресет, разовый AF) живут 2 с | Пресет, нажатый при обрыве связи, срабатывал минуты спустя |
| Приоритеты: EMERGENCY > MANUAL > TRACKING (pt) > TRACKING_ZOOM > QUERY | Задержка поворота из-за зума — неучтённая задержка в контуре регулятора, она раскачивает его |
| Стопы при выключении слежения — с приоритетом MANUAL | Иначе стоп уходил после `#R` и мог прервать вызов пресета |
| Окно для зума (`scheduler.py`): зум слежения, ждущий ≥ 0,3 с (`ZOOM_WINDOW_AFTER_S`), уходит раньше поворота слежения, если pt изменился меньше чем на 2 кода (`PT_SMALL_CHANGE`), если это отъезд (код < 50: человек у края) или если зум останавливает/разворачивает идущий наезд. Поворот уступает не больше одного окна подряд. Было: зум всегда за поворотом | Часть 0, A: зум ждал за поворотом до 2,4 с, камера 2,8 с продолжала наезд после решения остановиться. «Общая очередь» поднимала p95 поворота до 226 мс и давала раскачку «Резко». Отъезд у края держит человека в кадре при разгоне поворота (Review Focus 1). Тесты: `test_zoom_gets_window_without_delaying_pan_beyond_one_slot`, `test_zoom_waits_while_pan_changes_notably`, `test_zoom_stop_gets_window_while_pan_changes`, `test_zoom_out_gets_window_while_pan_changes` |
| Запрос положения (`#APC`, `#GZ`), прождавший ≥ 0,4 с (`QUERY_MAX_WAIT_S`), уходит следующим впереди слежения (TRACKING и TRACKING_ZOOM), но не впереди EMERGENCY и MANUAL; пульс после er2 по-прежнему идёт первым. Запрос, от которого вызывающий отказался по таймауту, убирается из очереди (future отменяется, поздний ответ молча отбрасывается). Было: QUERY — всегда последним, брошенный запрос оставался в очереди и уходил «в никуда» | Живая HE40 2026-10-30 (`tests/data/episodes/2026-10-30-he40-tele.zip`): слежение заново занимало ячейки pt и zoom каждый такт, ответов `#APC`/`#GZ` не было 10 с (запросы ждали до 7 с), регулятор считал скорости по зуму 0xF41, когда камера давно отъехала к 0xA38, и поворот качался. Запрос раз в секунду стоит повороту не больше одного окна 130 мс. Тесты: `test_query_not_starved_by_continuous_tracking`, `test_aged_query_goes_before_tracking_and_tracking_zoom`, `test_aged_query_never_preempts_emergency_or_manual`, `test_abandoned_query_is_not_sent` |
| Слушателей отправки несколько (`add_sent_listener`): запись и модель зума; сбой одного не мешает другим. В событии — `t`, начало отправки по часам планировщика | Модели зума нужен момент, когда команда ушла в камеру, а не когда слушатель получил ответ; запись берёт тот же `t` временем события `cmd`, поэтому повтор совпадает |
| Стоп фокуса `#F50` при ответе `eR3` не повторяется (`scheduler._on_failure`); стопы поворота и зума повторяются по-прежнему | Площадка 2026-10-29: при включённом автофокусе камера всегда отвечает `eR3:F50`, аварийный стоп слал его ~23 раза за 3 с и занимал очередь. Это единственное исключение из «аварийный стоп не теряется» |

## Распознавание и цель

| Решение | Почему |
|---|---|
| Детектор отдаёт всё от 0,10; новый трек — от 0,25 (по образцу ByteTrack) | На реальном общем плане докладчик за кафедрой даёт 0,29; на рабочей крупности — 0,89 |
| Цель сопоставляется **первой**. Одиночного кандидата отвергаем, только если внешность явно чужая (> 0,6); внешность решает лишь между несколькими кандидатами | Расстояние по одежде у одного и того же человека скачет 0,12–0,37 (MJPEG 640×360, тёмная сцена). Строгий порог 0,35 рождал «двойника», который навсегда перехватывал цель (135 потерь из 149 кадров) |
| Узнанная после пропажи цель сохраняет свой номер | Оператор видел «№3 → №25» |
| Гистограммы считаются вне замка трекера, только по прямоугольнику торса | Толпа зрителей подвешивала окно на 100+ мс |
| Анализ берёт 640×360 | На рабочей крупности результат тот же, что на 1280×720 |
| ONNX Runtime: DirectML, при сбое (в том числе при первом прогоне) — CPU; 3 потока, без busy-wait | Рядом работают vMix/OBS. На целевом ПК: 13–14 анализов/с, ~31 мс, DirectML |
| Трекер людей знает сдвиг картинки от команд камеры (`FramingController.image_motion` → `PersonTracker.update(motion=…)`): предсказанная рамка цели ищется и с поправкой, и без неё; скорость человека считается без сдвига | Прогон 4 «Резко» (2026-10-29): за 0,9 с картинка съехала на ~45×65 px, цель №2 потеряна на минуту. Модель по умолчанию отстаёт от камеры на ~0,25 с (на записи -38 px против -67 к 0,9 с), поэтому одной поправке не верим |
| Переход цели на новый трек: `ADOPT_WINDOW_S` 0,5 с, `ADOPT_IOU` 0,1, размер в `ADOPT_AREA_RATIO` 1,6 раза, только трек, появившийся после потери цели; внешность — не хуже `reid_hard_distance` | На записи «Резко» цель вернулась новым №3 через 0,37 с на предсказанном месте, рамка 34×72 против 35×67. IoU мал нарочно: сдвиг по модели неточен. Старые треки (другой человек) не берутся, окно 0,5 с — как в задании; дольше цель узнаёт внешность |

## Регулятор слежения

| Решение | Почему |
|---|---|
| Мастер калибровки: пробег ≤ `PROBE_MAX_FRACTION` = 0,4 кадра от старта (было 0,9); стоп заранее по прогнозу `x + v·STOP_LAG_S` (0,45 с) при угле ≥ `PREDICT_MIN_HFOV` = 20° и ≥ `MIN_FIT_SAMPLES` = 3 опросов; домой — до смены зума | Площадка 2026-10-29: pan ушёл на ~32° (больше полкадра 62°). 0,4: полкадра минус запас на инерцию. `STOP_LAG_S` 0,45 = опрос #APC (~0,13 с) + стоп + торможение 0,3 с (§3 живой замер); 0,8 и 1,2 на симуляторе не дали лучше (0x800: 0,79 и 0,84 против 0,84 кадра). `PREDICT_MIN_HFOV` 20°: на теле ранний стоп оставлял 2–3 замера и скорость кода 80 выходила 4,3 вместо 10 кадров/с (тест `waits_for_zoom_that_starts_late`). `MIN_FIT_SAMPLES` 3: минимум точек для подгонки скорости и разгона. **Честно:** полкадра держится только на широком угле (0,38 кадра). Код 90 на 0x800 и на теле проскакивает за один опрос: замерено 0,79–0,84 кадра на 0x800; там граница — не больше кадра и не дальше полкадра широкого угла (31°), иначе терялась бы точность таблицы. Тест: `test_wizard_never_goes_beyond_half_frame_from_start` |
| Прогноз стопа мастера идёт с первого опроса: скорость = max(`PRIOR_SPEED_FRACTION` 0,7 × паспортная скорость кода из `he42.PAN_DEG_S`, измеренная по двум последним опросам); раньше — только после `MIN_FIT_SAMPLES` опросов | После `RAMP_TAU_S` 0,37 → 0,12 код 90 на широком угле (61°/с) к третьему опросу уже у предела пробега: pan уходил на 35° (> полкадра 31°, тест `test_wizard_never_goes_beyond_half_frame_from_start`). С приором 0,7: 22,9–24,9°. **0,7 подобрано**, а не выведено: 0,5 не хватило (34,4°). **Цена:** код 90 на широком угле — 2 опроса, точность таблицы 11,7% (≈ на 12% хуже остальных кодов; эту ошибку на ходу исправляет подстройка скорости по `#APC`, `speed_adapt`, ×0,5…×2) (допуск в `test_wizard_near_pan_end…` для кода 90 — 0,15, было 0,1); остальные коды и угол ≥ 20° без изменений. Тест мастера: диапазон τ вокруг 0,12 (0,10–0,25 и 0,10–0,22; были 0,2–0,55 и 0,27–0,47 вокруг 0,37) — мастер честно находит τ симулятора |
| Компенсация задержки по модели камеры: мёртвое время 0,08 с + инерция τ 0,12 с (с 2026-10-29; было 0,37 — см. ниже) | Разгон живой камеры до 90% 0,27–0,33 с (замер 2026-10-29, τ 0,12 с); кадр опаздывает |
| `CameraDynamics.position(t)`, а не `displacement(0, t)` | После 10 с старые команды сворачиваются, и «смещение с момента 0» прыгало → на теле камера уезжала от человека |
| Мировые координаты делятся на масштаб зума | Иначе наезд выглядит как ходьба, и наезд идёт «ступеньками» |
| Скорость человека — наклон за 0,4 с; вес упреждения **1,0** (`FF_GAIN`, было 0,5). Рост упреждения плавный (`FF_RISE_S` 0,5 с), падение — сразу; пошёл — скорость середина между окном 0,4 с и тремя последними замерами (`START_BLEND` 0,5); человек два замера подряд позади прогноза больше 0,01 кадра (`STOP_INNOV`) — тормозит, скорость по трём последним замерам | Часть 0, C: с весом 0,5 установившаяся ошибка на ходу 0,076 кадра, с 1,0 — 0,019. Устойчивость к ошибке таблицы скоростей при полном упреждении держит подстройка по `#APC` (задача 5); плавный рост упреждения не даёт его петле раскачать камеру, пока поправка не найдена: ×2 при очереди 0,13 с без него раскачивалось за 5 с, с ним поправка успевает (×0,5…×2 — ≤ 1 разворота за 10 с стояния). Тесты: `test_lecture_walk_no_lag`, `test_no_swing_with_calibration_error_x05_x2`, `test_robust_when_camera_faster_than_model`, `test_camera_faster_than_table_adapts_while_walking` (за первое стояние разворотов теперь ≤ 1, было ≤ 2) |
| Ускорение и рывок ограничены у **движения камеры** по модели разгона: команда = скорость камеры + a·τ, |a| ≤ `a_max`, изменение a ≤ `j_max`; торможение — `BRAKE` 2,5 × (и рывок тоже); человек за мягкой зоной (или окажется там, пока камера ответит) — `CATCH_UP` 10 × (как может камера). «Обычно»: `a_max` 0,45 → 1,0 fw/s², новый `j_max` 4 fw/s³; «Мягко» 0,25 → 0,6 / 2; «Резко» 0,8 → 1,5 / 8. Без цели — стоп с `BRAKE`·a_max (было a_max). Было: сама команда разгонялась не быстрее a_max | Часть 0, C: на старте ходьбы камера ~0,7 с не может ответить, а запрет разгона (`a_max` 0,45) добавлял ещё v²/2a ≈ 0,5 кадра. Команда с ускорением a_max даёт камере ещё задержку τ (0,37 с) — ограничение по движению камеры её убирает. Тест `test_starts_smoothly_and_accel_limited` (ускорение и рывок камеры ≤ a_max и j_max; было: шаг команды ≤ a_max·dt), `test_no_target_ramps_to_zero` (≤ BRAKE·a_max·dt после пропажи), `test_walk_and_stop_like_operator` (ускорение камеры симулятора ≤ 1,2·BRAKE·a_max; было: по кодам ≤ 2,5·a_max — падал 2 из 3 на базе), `test_stored_sim_episode_replays_same_codes` (сводка повтора «макс. ускорение» — теперь камеры по модели разгона) |
| Потолок скорости — меньшее из `EffortProfile.v_max` («Мягко» 0,3 → 0,8, «Обычно» 0,5 → 1,2, «Резко» 0,8 → 1,2 fw/s) и возможности камеры на текущем зуме (`Calibration.pan_max_fw`, код 99 с поправкой задачи 5; наклон — по поправке наклона) | Часть 0, C: при потолке 0,5 человек на «Поясе» (0,77 fw/s) держался в кадре только отъездом зума втрое. «Мягко ↔ Резко» меняет плавность и зоны, но догоняют все (тест `test_every_effort_can_catch_a_walking_speaker`) |
| Торможение заранее: ошибка для догона — какой она станет, когда камера ответит: + v_человека·(мёртвое время + τ) − тормозной путь камеры по уже отданным командам (`CameraDynamics.coast`). Если по инерции камера проскочит человека — догон 0, остаётся упреждение (назад не командуем) | Без этого перелёт v_max 1,2 + FF 1,0 — 0,59 кадра и раскачка (часть 0, C). Тест `test_coast_is_stopping_distance`, `test_stop_settles_without_snap_back` |
| Трогаемся, только когда человек вышел из мёртвой зоны; «пошёл» — смещение в одну сторону за 0,4 с (`WALK_WINDOW_S`) не меньше max(1,2·мёртвая зона, 0,06 кадра) (`WALK_SHIFT` 0,8 → 1,2, новый `WALK_SHIFT_MIN`) со скоростью того же знака; гистерезис — половина смещения и `STOP_V`. | Состояние «ведёт» — синее, не зелёное | Красный и зелёный по вещательной традиции заняты Tally (эфир / предпросмотр). Синий совпадает с рамкой цели «ВЕДУ» на видео |
| Плитка состояния имеет постоянную высоту 118 | Кнопки под ней не должны смещаться при смене состояния; так просил пользователь |
| Tally показан рамкой вокруг видео, как на мультивьюере ATEM | Оператор смотрит на видео, рамка видна периферийным зрением |
| Tally «в эфире / не в эфире» только после TlIn с последнего hello, иначе «неизвестно» | Ложное «не в эфире» позволило бы двигать живую камеру |
| Tally только показывает эфир и ничего не блокирует | Решение пользователя (2026-10-22): защиту эфира держат флажки оператора, Tally — подсказка для глаз |
| Цвета — только в `ui/theme.py` (охраняет `test_no_hardcoded_colors`), основные размеры — там же | Прежде цвета были разбросаны по виджетам и расходились |

## Геймпад DualSense (2026-10-30)

| Решение | Почему (и во что обходится ошибка) |
|---|---|
| Мёртвая зона 0,12, дальше линейно до 1 (`mapping.DEADZONE`) | Дрейф стика DualSense — единицы процентов; кривая линейная по спеке (квадратичная — в BACKLOG по отзыву) |

| Автоповтор ириса: через 0,4 с, затем 6 шагов/с (`REPEAT_*`) | Одиночное нажатие = один шаг, удержание не «убегает»; подбор на площадке |

| Вибрация — на полной силе (1,0 / 1,0), короткие импульсы не короче 120 мс (в спеке было ~80 мс, 0,5 силы) | Замер на живом DualSense (Mac, Bluetooth): 0,5 × 200 мс не чувствуется, 1,0 × 1000 мс чувствуется. Цена: импульсы грубее задуманного, подстроить на площадке |

Цена: нет импульса упора при очень медленном нажатии |

| Перед абсолютным ирисом всегда `iris_auto(False)` | Признаку авто-ириса в ответе камеры не доверяем; лишняя команда склеивается планировщиком |
| L1/R1 — только размер (пояс → в рост → общий), назад к последней стороне пояса | Решение пользователя (2026-10-30). Цена: сторону пояса меняют окном или клавишами |
| Ручной фокус из меню — не дольше 3 с за нажатие (`FOCUS_MAX_S`); меню закрывается само через 10 с | Геймпад не шлёт повторов, чтобы обновить сторожа; потеря отпускания не должна увести фокус. Цена: длинную подстройку нужно нажать повторно |
| Правый стик (сосед) работает и при открытом меню | Спека: стики работают как обычно. Цена: случайная смена цели при работе в меню |
| Create: короткое нажатие — следующая камера, удержание — сохранить момент (как F9) | Решение пользователя (2026-10-30) |
| Заряд: уровень SDL (`get_power_level`) как верхняя граница — 5/20/70/100 %, «wired» — заряжается; оценка до разряда — по скорости падения, пока данных мало — «считаю…» | До 1.1.1 процент (шаг 10 %) читали из сырого отчёта DualSense через своё `SDL_hid_open`. На Mac его закрытие гонялось с потоком чтения SDL и роняло программу (2026-11-05, два отчёта о падении); точность заряда не стоит падения |
| Огоньки игрока = номер клетки камеры геймпада (1…4); поле «Номер на геймпаде» убрано из настроек | Решение пользователя (2026-11-05): с сеткой номер клетки виден на экране и не может разойтись с огоньками. `CameraConfig.pad_number` ещё читается из старого config.json, но не используется. Устанавливается через ctypes (`SDL_GameControllerSetPlayerIndex`) — в PyInstaller/Windows поиск библиотеки может отличаться |
| SDL: драйвер видео `dummy` + `display.init`, окно не создаётся | Без этого не работает `event.pump` в pygame-ce |
| Значок геймпада — без эмодзи в тексте (иконка + «2 · 60% · ≈3 ч 10 мин») | Иконка перекрашивается в цвет состояния (заряд ≤ 20 % — жёлтый); эмодзи дублировал бы иконку |
| Геймпад проверен на Mac по Bluetooth; USB и Windows — на площадке (шаг в LIVE_TEST_PROMPT) | У разработчика нет Windows; SDL HIDAPI одинаков для USB и BT, BT — трудный путь |

## Несколько камер (2026-10-31…11-05)

| Решение | Почему |
|---|---|
| `max_analyzed = 1` по умолчанию (1…4, меню ☰) | Замер: на GTX 1650 одна камера даёт 13–14 к/с анализа; две не замерены. Лучше одна работающая, чем две вялые. Тест на симуляторе с двумя (`test_multi_sim_slow.py`) идёт на быстрой машине и ничего не говорит о GTX 1650 |
| Анализ не отнимают у камеры со слежением | Слежение без свежих кадров анализа останавливает камеру; выбор другой клетки не должен ничего выключать в эфире |
| Скорости клавиатуры, мыши и геймпада на одну камеру складываются (сумма ±1) | Как до сетки в одном окне; оператор может одной рукой жать стрелки, другой вести стик. Любой источник выключает слежение |
| После Esc held-стик «залипает» до возврата в центр (`latch`), в том числе у неактивных источников | Иначе стик, зажатый в момент Esc, мгновенно снова двигал бы камеру |
| Огоньки геймпада = номер клетки | См. «Геймпад» |
| Create передвигает геймпад на следующую камеру, а не просто выбирает клетку | Геймпад должен вести ту камеру, чьи огоньки на нём горят; выбор клетки — отдельное действие мыши |
| Тачпад останавливает только камеру своего геймпада | Остальные камеры могут вести слежение в эфире |
| R3, L1, R1 действуют, только если камера геймпада выбрана; иначе вибрация «некуда» | Автовыбор двигал бы правую панель и клавиатуру из-под рук оператора (ревью 2026-11-05) |
| Выбор клетки не снимает флажки агента | Решение главной сессии 2026-11-05: флажки теперь у камеры, а не у окна. Условия держат `tests/ui/test_agent_flags_per_camera.py`: ручное действие на B (клавиатура, мышь, геймпад, пресет) снимает флажки только B; Esc — все |
| До четырёх геймпадов — один поток SDL (`SdlHub`) | SDL нельзя безопасно опрашивать из нескольких потоков; представления `SdlBackend(hub, i)` читают общий поток |
| `SDL_JOYSTICK_MFI=0` до запуска SDL (`gamepad/device.py`) | MFi-драйвер SDL зовёт `IOS_AddJoystickDevice` из очереди GameController: он берёт замок джойстиков SDL и крутит вложенный цикл, где Qt рисует на Python и ждёт GIL; поток опроса держит GIL и ждёт тот же замок — зависание при подключении DualSense (2026-11-06, снимок `sample`). DualSense и так идёт через HIDAPI; после отключения — два переподключения под перерисовкой Qt на Python без зависания |
| SDL запускает (`hub.open`) сам поток `MultiPadThread`, не поток Qt | На macOS SDL вешает события HID на цикл потока, где его запустили. В 1.1.0 запуск шёл из окна: события приходили в цикл Qt, пока фоновый поток опрашивал — куча портилась, падение через 1,5–7 мин с DualSense (2026-11-05). После переноса — 8 мин под циклом Qt без сбоев |
| Пересканирование не закрывает «дубль», если pygame вернул тот же объект | pygame-ce на `Controller(i)` для открытого устройства отдаёт тот же объект; в 1.1.0 его `quit()` отключал свой же геймпад каждые 0,5 с («геймпад прыгает») |
| L1/R1 — скорость стика (`SpeedStep`), режим у каждого геймпада: «Предел скорости» (по умолчанию; ступени — ниже) или «Чувствительность» ±10; крупность — свайп по тачпаду (≥ 1/3 ширины, ≤ 0,8 с, без нажатия) | Пользователь, 2026-11-06. Пробник на DualSense: x 0…1, свайп 0,1–0,4 с. Вибрация: шаг — толчок 120 мс (короче не чувствуется, замер в `feedback.py`), край — толчок 400 мс. Ступень применяется в `GamepadBridge.velocity()`, поэтому она одинаково действует на сложение скоростей и упор (`LimitWatch`) |
| Ступени L1/R1 — скорость на упоре стика в °/с: 3, 5, 8, 13, 21, 34, 55, 90 (`manual_curve.PAD_GEAR_DEG_S`, каждая ≈ ×1,6); по умолчанию 6 (34 °/с). Внутри ступени `shape(наклон)` — доля этой скорости в °/с, в код камеры — обратной таблицей `he42.PAN_DEG_S` (`pad_velocity`) | Жалоба пользователя 2026-11-06: «в крайнем положении прям сильнее» и мало ступеней. При раскладке по кодам (как 1.1) таблица камеры крутая к краю: стик 80 % — 33 °/с, 90 % — 58, упор — 90; последняя пятая часть хода давала 63 % скорости. Теперь — 42 % (тест `test_no_burst_at_the_edge_of_the_stick`). Прежние ступени 25–100 % резали код и давали 4 / 22 / 52 / 90 °/с — неровно. Цена: на 90 °/с середина хода быстрее, чем в 1.1 (50 % — 17 °/с вместо 2), поэтому по умолчанию 34 °/с. Код 99 (90 °/с) не мерялся — его даёт только верхняя ступень. Мышь и стрелки — по-прежнему по кодам |
| Вверх/вниз левого стика — своя кривая (`Mapper.tilt_sensitivity`; нет записи — как влево/вправо) и скорость, % от влево/вправо, 20–100, по умолчанию 60 (`config.DEFAULT_TILT_SPEED`); у каждого геймпада | Пользователь, 2026-11-06: «при вертикальном движении реагирует как будто резче». Камера наклоняет с теми же °/с, что и поворачивает (§7), но кадр 16:9 по высоте ≈ 56 % ширины — те же °/с проносят кадр по вертикали почти вдвое быстрее. Скорость — множитель ступени в `GamepadBridge.velocity()`; мышь и стрелки не меняются |
| При подключении геймпада мост не защёлкивается повторно | Собственный latch автомата уже покрывает стик, зажатый при подключении; второй latch в потоке Qt глушил стик, сдвинутый сразу после подключения |
| Закрытие клетки: аварийный стоп сразу, остановка сессии — в фоновом потоке | `stop()` на мёртвом IP занимал ~0,5 с в потоке Qt |

## Чувствительность ручного управления (2026-11-05, версия 1.1)

| Решение | Почему |
|---|---|
| Кривая «наклон → скорость» `|v|^e` со знаком, `e = 3 − 2·sens/100` (`control/manual_curve.py`); ползунок 0 («Плавно», e = 3) … 100 («Резко», e = 1 — линейно, как 1.0.1); по умолчанию 50 (e = 2) | Жалоба пользователя: стик резкий. Таблица камеры сама крутая: код 63 — 3,8 °/с, 75 — 22 °/с, 99 — 90 °/с (`he42.PAN_DEG_S`), поэтому линейная кривая до кода 49 почти весь ход стика отдаёт быстрым скоростям. Степень 2: половина наклона — код 63 (3,8 °/с) вместо 75 (22 °/с); полный наклон — по-прежнему 99 |
| После кривой скорость не меньше 0,02 (код 52), если до кривой наклон её давал | `velocity_to_code` ниже 0,02 даёт код 50 (стоит): при e = 3 мёртвая зона выросла бы с 2 % до 27 % хода |
| Кривая — у источника (мышь, стрелки, каждый геймпад после мёртвой зоны в `Mapper`), до смесителя; зум и фокус она не трогает | Смеситель складывает уже «оформленные» скорости источников; у каждого геймпада своя настройка по серийному номеру SDL (иначе `GUID:имя` — одинаковые без серийного делят настройку) |
| Стрелки — тоже через кривую: `shape(0,4, sens)` | Решение пользователя: «одна настройка для мыши и клавиш». По умолчанию это 0,16 (код 59, ≈1,3 °/с) вместо 0,4 (код 70, ≈13,6 °/с) — сказано в CHANGELOG; при «Резко» как было |
| «Медленнее на крупном плане»: множитель `hfov(зум)/hfov(широкий)` не меньше 0,15, только ручной поворот (`VelocityMixer.pt_scale`); зум — из `#GZ`, окно спрашивает его раз в секунду на камеру, пока флажок включён | Решение пользователя. Регулятор слежения шлёт `#PTS` мимо смесителя и множителя не видит (тест). 0,15 — чтобы полный наклон на теле ещё двигал камеру (код 57); сама камера на теле тоже замедляется (`tele_pan_ratio`) — вместе может оказаться слишком медленно, проверить на площадке |
| Gain с «Авто» с крестовины: первое нажатие — последнее виденное ручное значение, иначе 0 dB, без шага | Решение пользователя 2026-11-05: раньше без виденного ручного значения нажатие ничего не делало. Картинка может стать темнее — принято |
| Флажок «Авто» ириса в панели — по ответам камеры (`ImageState.iris_auto`) | Жалоба «ирис с крестовины не снимает авто»: камера (симулятор) авто снимала, но панель режим ириса не читала, и флажок оставался |

## Своя зона слежения мышью (2026-11-06)

| Решение | Почему |
|---|---|
| Зона = точка лица (x, y) + масштаб обеих зон; хранится у камеры для каждой крупности (`CameraConfig.zones`, `control/zones.py`) | Набросок «Зона кадра · тяните» (`docs/design/mockups/drawer-and-frame.html`), согласован 2026-11-05; у «Пояса» и «Общего» лицо стоит в разных местах |
| Точка не ближе 10 % к краю; масштаб 0,5…1,8; мягкая зона не больше половины кадра | 1,8 — самая широкая мягкая зона («Мягко», 0,25) ещё в кадре; у края лицо обрезается при любой ошибке регулятора |
| Перенос зоны не выключает слежение и не снимает флажки агента; камера доезжает до точки обычным регулятором | Как смена крупности: это настройка кадра, а не ручное движение камеры |
| Нажатие в зоне выбирает человека при отпускании, если мышь сдвинулась меньше 6 px; вне зоны — сразу, как раньше | Цель почти всегда внутри зоны: иначе зону нельзя было бы взять, не перевыбрав цель |
| В чёрный ящик рядом с ключом композиции пишется точка лица (`anchor`); разбор записи её берёт | Без неё `--replay` вёл бы к точке по умолчанию |

## Запись видео и нагрузка (2026-11-08, версия 1.3)

| Решение | Почему |
|---|---|
| MP4 фрагментами (`frag_keyframe+empty_moov+default_base_moof`), а не обычный MP4 | Обычный MP4 без финальной записи `moov` не читается. Опыт: PyAV 19.0.1, копия H.264, `os._exit` посреди записи — из 200 пакетов прочитано 189, файл открывается |
| Своё RTSP-подключение к `h264_1`, даже если окно смотрит этот поток | Окно и анализ часто на MJPEG 640×360; сбой записи не должен трогать их. Риск: второе подключение к камере (2026-10-29 отказы на 2–3 с при нескольких клиентах) — проверить на площадке; повторы 2, 5, 10 с |
| Поток нельзя скопировать — переход на «Лёгкий файл» с сообщением | Настоящий поток HE42 с Mac недоступен; REC не должен гореть без записи |
| Пороги запаса: < 20 мин оранжевый, < 5 мин красный, < 1 мин автостоп; оценка 11,5 ГБ/ч на камеру («лёгкий» 1,4 ГБ/ч), пока нет фактической скорости | Решение пользователя по макету `recording-controls.html`; 25 Мбит/с — оценка, настоящий битрейт замерить на площадке |
| Части файла на FAT32 — 3 900 000 000 байт, по ключевому кадру | Предел FAT32 — 4 ГиБ; следующая часть начинается с ключевого кадра, пропусков нет |
| Нагрузка: > 85 % оранжевым, > 95 % красным; проценты от всего компьютера; GPU — самый занятый тип движка, как в Диспетчере задач | Решение пользователя по макету; сумма типов движков дала бы больше 100 % |
| «Лёгкий файл»: `libx264`, средний битрейт 3 Мбит/с, `maxrate` 6 Мбит/с, `bufsize` 3 Мбит (полсекунды: за любую секунду не больше ~1,5 предела), 25p | Решение пользователя 2026-11-09: на движении можно подскакивать до 6. Без `maxrate` x264 в режиме среднего битрейта всплесков не ограничивает. Тест `test_max_rate_limits_bursts` |
| Нагрузка в нижней строке вместо «разрешение» и «к/с» (вариант 1 макета `load-placement.html`); эти значки — только при сбое | Решение пользователя 2026-11-09: шапка забита; числа есть в углу видео, а значки нужны как показ сбоя и меню потока |
| Доля программы в GPU на Mac — «—» | `ioreg` даёт только общую загрузку, по процессам нужны права администратора |
