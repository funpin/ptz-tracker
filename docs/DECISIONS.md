# Решения и их причины

Каждое решение подтверждено замером или тестом. Прежде чем менять какое-то из них, воспроизведите исходную проблему тестом: значения кажутся произвольными, но за каждым стоит конкретный сбой.

## Камера и видео

| Решение | Почему |
|---|---|
| Видео для слежения — **MJPEG** `http://IP/cgi-bin/mjpeg?resolution=640x360&framerate=25`; в «Авто» он первый | Живая HE42: «команда → движение в кадре» 344 мс у MJPEG против ~830 мс у H.264 (stream_1 и stream_2): буфер декодера H.264 добавляет ~0,5 с |
| RTSP-адрес H.264 — `/MediaInput/h264/stream_1` (и `stream_2`) | `/MediaInput/h264` и `/MediaInput/stream_1` отвечают 5XX. Режим камеры «Internet mode (over HTTP)» должен быть выключен |
| Интервал команд по умолчанию 130 мс, параметр в настройках камеры | Так в спецификации Panasonic. Запросы `#O` проходили и при 50 мс, команды движения на таком темпе не проверены |
| Перехват пультом определяется опросом `#APC`/`#GZ` | Уведомления камеры (`cgi-bin/event?connect=start`) регистрируются (HTTP 204), но не пришло ни одного; опрос раз в 0,7 с видит движения пульта надёжно |
| Замеры HE42 живут в `camera/he42.py` и больше нигде | Симулятор и модель регулятора однажды разошлись в 1,7 раза: проверка слежения на симуляторе обманывала |

## Планировщик команд

| Решение | Почему |
|---|---|
| Склейка по ключу (`pt`, `zoom`, …) + «только если изменилось» + возврат к отправленному значению отменяет ожидающую команду | Камера принимает ~7 команд/с; оператор и регулятор шлют намного чаще |
| `er2` (занята, например пультом) и EMERGENCY повторяются до успеха; `er1`/`er3` — не больше 3 раз | Стоп, отброшенный после трёх «занята», оставлял камеру в движении в эфире |
| Разовые команды (пресет, разовый AF) живут 2 с | Пресет, нажатый при обрыве связи, срабатывал минуты спустя |
| Приоритеты: EMERGENCY > MANUAL > TRACKING (pt) > TRACKING_ZOOM > QUERY | Задержка поворота из-за зума — неучтённая задержка в контуре регулятора, она раскачивает его |
| Стопы при выключении слежения — с приоритетом MANUAL | Иначе стоп уходил после `#R` и мог прервать вызов пресета |
| Окно для зума (`scheduler.py`): зум слежения, ждущий ≥ 0,3 с (`ZOOM_WINDOW_AFTER_S`), уходит раньше поворота слежения, если pt изменился меньше чем на 2 кода (`PT_SMALL_CHANGE`), если это отъезд (код < 50: человек у края) или если зум останавливает/разворачивает идущий наезд. Поворот уступает не больше одного окна подряд. Было: зум всегда за поворотом | Часть 0, A: зум ждал за поворотом до 2,4 с, камера 2,8 с продолжала наезд после решения остановиться. «Общая очередь» поднимала p95 поворота до 226 мс и давала раскачку «Резко». Отъезд у края держит человека в кадре при разгоне поворота (Review Focus 1). Тесты: `test_zoom_gets_window_without_delaying_pan_beyond_one_slot`, `test_zoom_waits_while_pan_changes_notably`, `test_zoom_stop_gets_window_while_pan_changes`, `test_zoom_out_gets_window_while_pan_changes` |
| Слушателей отправки несколько (`add_sent_listener`): запись и модель зума; сбой одного не мешает другим. В событии — `t`, начало отправки по часам планировщика | Модели зума нужен момент, когда команда ушла в камеру, а не когда слушатель получил ответ; запись берёт тот же `t` временем события `cmd`, поэтому повтор совпадает |

## Распознавание и цель

| Решение | Почему |
|---|---|
| Детектор отдаёт всё от 0,10; новый трек — от 0,25 (по образцу ByteTrack) | На реальном общем плане докладчик за кафедрой даёт 0,29; на рабочей крупности — 0,89 |
| Цель сопоставляется **первой**. Одиночного кандидата отвергаем, только если внешность явно чужая (> 0,6); внешность решает лишь между несколькими кандидатами | Расстояние по одежде у одного и того же человека скачет 0,12–0,37 (MJPEG 640×360, тёмная сцена). Строгий порог 0,35 рождал «двойника», который навсегда перехватывал цель (135 потерь из 149 кадров) |
| Узнанная после пропажи цель сохраняет свой номер | Оператор видел «№3 → №25» |
| Гистограммы считаются вне замка трекера, только по прямоугольнику торса | Толпа зрителей подвешивала окно на 100+ мс |
| Анализ берёт 640×360 | На рабочей крупности результат тот же, что на 1280×720 |
| ONNX Runtime: DirectML, при сбое (в том числе при первом прогоне) — CPU; 3 потока, без busy-wait | Рядом работают vMix/OBS. На целевом ПК: 13–14 анализов/с, ~31 мс, DirectML |

## Регулятор слежения

| Решение | Почему |
|---|---|
| Компенсация задержки по модели камеры: мёртвое время 0,08 с + инерция τ 0,37 с | Разгон живой камеры до 90% ~0,85 с; кадр опаздывает |
| `CameraDynamics.position(t)`, а не `displacement(0, t)` | После 10 с старые команды сворачиваются, и «смещение с момента 0» прыгало → на теле камера уезжала от человека |
| Мировые координаты делятся на масштаб зума | Иначе наезд выглядит как ходьба, и наезд идёт «ступеньками» |
| Скорость человека — наклон за 0,4 с; вес упреждения **1,0** (`FF_GAIN`, было 0,5). Рост упреждения плавный (`FF_RISE_S` 0,5 с), падение — сразу; пошёл — скорость середина между окном 0,4 с и тремя последними замерами (`START_BLEND` 0,5); человек два замера подряд позади прогноза больше 0,01 кадра (`STOP_INNOV`) — тормозит, скорость по трём последним замерам | Часть 0, C: с весом 0,5 установившаяся ошибка на ходу 0,076 кадра, с 1,0 — 0,019. Устойчивость к ошибке таблицы скоростей при полном упреждении держит подстройка по `#APC` (задача 5); плавный рост упреждения не даёт его петле раскачать камеру, пока поправка не найдена: ×2 при очереди 0,13 с без него раскачивалось за 5 с, с ним поправка успевает (×0,5…×2 — ≤ 1 разворота за 10 с стояния). Тесты: `test_lecture_walk_no_lag`, `test_no_swing_with_calibration_error_x05_x2`, `test_robust_when_camera_faster_than_model`, `test_camera_faster_than_table_adapts_while_walking` (за первое стояние разворотов теперь ≤ 1, было ≤ 2) |
| Ускорение и рывок ограничены у **движения камеры** по модели разгона: команда = скорость камеры + a·τ, |a| ≤ `a_max`, изменение a ≤ `j_max`; торможение — `BRAKE` 2,5 × (и рывок тоже); человек за мягкой зоной (или окажется там, пока камера ответит) — `CATCH_UP` 10 × (как может камера). «Обычно»: `a_max` 0,45 → 1,0 fw/s², новый `j_max` 4 fw/s³; «Мягко» 0,25 → 0,6 / 2; «Резко» 0,8 → 1,5 / 8. Без цели — стоп с `BRAKE`·a_max (было a_max). Было: сама команда разгонялась не быстрее a_max | Часть 0, C: на старте ходьбы камера ~0,7 с не может ответить, а запрет разгона (`a_max` 0,45) добавлял ещё v²/2a ≈ 0,5 кадра. Команда с ускорением a_max даёт камере ещё задержку τ (0,37 с) — ограничение по движению камеры её убирает. Тест `test_starts_smoothly_and_accel_limited` (ускорение и рывок камеры ≤ a_max и j_max; было: шаг команды ≤ a_max·dt), `test_no_target_ramps_to_zero` (≤ BRAKE·a_max·dt после пропажи), `test_walk_and_stop_like_operator` (ускорение камеры симулятора ≤ 1,2·BRAKE·a_max; было: по кодам ≤ 2,5·a_max — падал 2 из 3 на базе), `test_stored_sim_episode_replays_same_codes` (сводка повтора «макс. ускорение» — теперь камеры по модели разгона) |
| Потолок скорости — меньшее из `EffortProfile.v_max` («Мягко» 0,3 → 0,8, «Обычно» 0,5 → 1,2, «Резко» 0,8 → 1,2 fw/s) и возможности камеры на текущем зуме (`Calibration.pan_max_fw`, код 99 с поправкой задачи 5; наклон — по поправке наклона) | Часть 0, C: при потолке 0,5 человек на «Поясе» (0,77 fw/s) держался в кадре только отъездом зума втрое. «Мягко ↔ Резко» меняет плавность и зоны, но догоняют все (тест `test_every_effort_can_catch_a_walking_speaker`) |
| Торможение заранее: ошибка для догона — какой она станет, когда камера ответит: + v_человека·(мёртвое время + τ) − тормозной путь камеры по уже отданным командам (`CameraDynamics.coast`). Если по инерции камера проскочит человека — догон 0, остаётся упреждение (назад не командуем) | Без этого перелёт v_max 1,2 + FF 1,0 — 0,59 кадра и раскачка (часть 0, C). Тест `test_coast_is_stopping_distance`, `test_stop_settles_without_snap_back` |
| Трогаемся, только когда человек вышел из мёртвой зоны; «пошёл» — смещение в одну сторону за 0,4 с (`WALK_WINDOW_S`) не меньше max(1,2·мёртвая зона, 0,06 кадра) (`WALK_SHIFT` 0,8 → 1,2, новый `WALK_SHIFT_MIN`) со скоростью того же знака; гистерезис — половина смещения и `STOP_V`. Было: размах за 1,5 с ≥ 0,8 мёртвой зоны | Покачивание у кафедры ±3% кадра раскачивало камеру. Размах за 1,5 с не отличал переминание от ходьбы: при ±0,06 и «Обычно»/«Резко» камера ходила в 2,5–5 раз шире человека, сторож срабатывал (BACKLOG, задача 2); теперь камера ходит 0,06–0,10 при размахе человека 0,12, сторож молчит. Тест `test_sway_shuffle_does_not_trip_watchdog_or_overswing` |
| После перелёта назад (против того, куда камера шла за человеком, а человек туда не идёт): со скоростью `RETURN_GAIN` 2,5 × ошибка, не быстрее `RETURN_V_SOFT` = 1,5·`SETTLE_V` в мягкой зоне и `RETURN_V_MAX` 0,25 за ней; `SETTLE_V` 0,06 → 0,08. «Человек пошёл назад» — упреждение в ту сторону ≥ `WALK_BACK_V` 0,1 и камера уже не катится «туда»; направление забывается через 3 с стояния (`RETURN_WINDOW_S`) | Тормозной путь камеры ≈ v·0,6–0,8 с — перелёт неизбежен; дёргать обратно — «пинг-понг». Review Focus 5: средняя ошибка 1–5 с после остановки ≤ 0,08 при 0,06 не выходила (0,084–0,126 при 0,31–0,35 fw/s); с 0,08 — 0,074. Кажущееся «назад» при торможении (ошибка задержки, очередь 0,13 с) давало рывок назад до 1,2 fw/s. Тесты `test_stops_without_overshoot_after_walk`, `test_stop_settles_without_snap_back` |
| Человек уходит за край быстрее камеры: прогноз наибольшей ошибки, пока камера догоняет (`escape` = ошибка + v_отн·(мёртвое время + τ) + v_отн²/(2·BRAKE·a_max)) больше `ESCAPE_ERR` 0,4 — сразу отъезд `ESCAPE_ZOOM` 0,6 ln/с (разгон зума ×10); ошибка больше `EDGE_ZOOM_ERR` 0,3 — отъезд 1,5·zoom_max (разгон ×2). Было: отъезд zoom_max при ошибке больше мягкой зоны. При отъезде доворот за зумом, уводящий камеру от уходящего за край, не делается. Пропал у края, уходя, — камера ещё `LOST_COAST_S` 0,4 с идёт за ним с его скоростью | Было: на 1,25 м/с («walk») человек уходил из кадра на каждой ходьбе вправо и терялся до следующего прохода. На прохаживании (≤ 0,35 fw/s) отъезда нет (зум ≤ ×1,3). Отъезд 0,8 ln/с при неверной таблице зума ×1,5 уводил модель зума на 23% (`test_zoom_model_corrected_by_gz`), 0,6 — 15%. Тесты `test_fast_walk_stays_in_frame`, `test_fast_walk_not_lost_on_projective_sim`, `test_lecture_walk_no_lag` |
| Сторож: 3 **настоящих** разворота за 6 с → стоп и «Сервис → Калибровка» (`SwingWatch`). Разворот засчитывается, если команда сменила знак, пройдя через \|v\| > 0,03 fw/s (`WATCHDOG_MOVING_V`, наклон — ×9/16); новое направление дал не доворот за зумом (без него команда тоже за порогом); пик ошибки между разворотами больше **всей** мягкой зоны (`WATCHDOG_ERR_FRACTION` 0,6 → 1,0) и не меньше прошлого пика (`WATCHDOG_GROWTH` 1,0); по `#APC` камера за полупериод проехала ≥ 0,02° (`WATCHDOG_APC_MIN_DEG`, в единицах — по `he42.APC_DEG_PER_UNIT`, шкала симулятора) и не в ту же сторону, что в прошлом. Нет двух ответов `#APC` за полупериод — решают команды. **Второе правило — «человек стоит, камера ходит»:** настоящий разворот засчитывается при любой ошибке, если человек «в мире» сдвинулся меньше мёртвой зоны с разворота в ту же сторону (период назад: ошибка модели камеры в одной фазе одинакова и вычитается), а камера за полупериод проехала по командам больше мягкой зоны. Было: любая смена знака команды при ошибке > 0,6 мягкой зоны | На эфире раскачка хуже остановки. Часть 0, B3: из 72 засчитанных разворотов 61% — при \|v\| < 0,02 (камера стоит), 81% — во время зума; порог 0,13 кадра меньше обычного отставания на ходу. «Зум не едет» буквально ослеплял сторож: настоящая раскачка ×3 идёт с отъездом у края, и её развороты все во время зума — поэтому исключается только разворот, сделанный доворотом за зумом. Повтор 10 первых тревог части 0: 0 из 10 (было 10). Виртуальный стенд, очередь 0,13 с: ×2 срабатывает на 18 с (было 13 с), ×3 — на 5,7 с (было 5,6), ×1,7 и ×0,5 молчат. Качание при стоящем человеке («Резко», задержка видео 0 у регулятора: наклон ±0,12 кадра с периодом ~3 с после наезда) — второе правило останавливает через ~8 с качания (31 с прогона); с верной задержкой — молчит. Остановка после ходьбы и покачивание у кафедры (±0,025–0,04 при «Обычно») не срабатывают; при ±0,06 и «Обычно»/«Резко» камера раскачивается в 2,5–5 раз шире человека — срабатывает. Сама запись B4 до своей остановки дала лишь 2 разворота быстрее 0,03 fw/s — по ней не поймать. Тесты: `test_watchdog_ignores_reversals_below_moving_speed`, `test_watchdog_ignores_reversals_during_zoom`, `test_watchdog_needs_large_and_growing_error`, `test_watchdog_confirms_reversals_by_apc`, `test_watchdog_still_catches_real_divergence_x2`, `test_watchdog_part0_false_alarms_gone`, `test_watchdog_counts_hunting_while_person_stands`, `test_watchdog_stops_hunting_on_standing_person`, `test_watchdog_quiet_on_settle_and_lectern_sway` |

Тесты сторожа, где нужна раскачка: ×2 без подстройки — по-прежнему ловит (~7 с), ×2,5 — ~5,6 с, ×3 — ~5,4 с; «стоящий» сценарий B4 пересоздан на ошибке задержки 0 вместо 0,3 (0 вместо 0,15 теперь затухает сам) | С полным упреждением и отъездом при уходе раскачка при ×2–2,5 идёт под непрерывный отъезд: каждый разворот начинал доворот за зумом, и сторож его не засчитывал — камера качалась ±0,3 кадра без остановки (`test_never_sustained_oscillation_either_stable_or_stopped`). `WATCHDOG_GROWTH` 0,9 тоже ловил её, но давал ложные срабатывания на быстрой ходьбе на симуляторе — оставлен 1,0. | Догон без ограничения ускорения (`CATCH_UP`) — только поворот; наклон — с a_max | На быстрой ходьбе с отъездом ошибка наклона большая от модели зума (отстаёт при отъезде 0,6 ln/с), резкий наклон за ней давал настоящие развороты и ложное «раскачивалась» на симуляторе (2 из 6 прогонов `test_fast_walk_not_lost_on_projective_sim`; после — 0 из 10) |
| «Пошёл» медленно: за `CALM_WINDOW_S` в одну сторону больше 0,16 кадра (`WALK_SLOW_SHIFT`) и скорость того же знака | С порогом за 0,4 с не меньше 0,06 кадра медленная ходьба на общем плане («Рост», ~0,12 fw/s) не считалась ходьбой — упреждения не было, ошибка 0,13–0,14 (`test_follows_walking_sim_person`, < 0,10). ## Симулятор и тесты

| Решение | Почему |
|---|---|
| Симулятор отдаёт `t_capture` = момент получения (отрисовка + задержка) | Как у живой камеры; иначе задержка вычиталась дважды |
| Скорости симулятора = `he42.PAN_FW_S` × угол обзора на широком угле | Тогда в долях кадра скорость совпадает с моделью на любом зуме |
| Критерии тестов поведения — по замерам: человек в кадре, обратный ход ≤ 1,5·`SETTLE_V`, развороты, ускорение **камеры** (а не «скачок кода»). Review Focus части 1 (задача 4): на прохаживании ≤ 0,35 fw/s без первой 1 с ходьбы средняя ошибка ≤ 0,05, до края ≥ 0,15, отъезд ≤ ×1,3; на быстрой ходьбе — человек в кадре (нос не дальше 0,08 за краем), цель не теряется дольше 1 с; после остановки средняя ошибка 1–5 с ≤ 0,08 | «Перелёт ≤ 2,5% кадра» физически невозможен для этой камеры; коды скорости нелинейны. Первую 1 с ходьбы быстрее не догнать: видео 0,15 + очередь + мёртвое время 0,08 + разгон τ 0,37 (часть 0, C) |
| Тесты замкнутого контура — на откалиброванной камере плюс отдельный тест без калибровки | Штатный режим — после мастера калибровки |
| Кадр симулятора проективный (`sim/projection.py`, по умолчанию; `projection="flat"` — прежний): поворот pan/tilt, f = (W/2)/tan(hfov/2), hfov 62,1°→3,3° по паспорту (`he42.HFOV_*`), бочка x·(1 + k1·r²) с k1 = −0,08 на широком угле → 0 на теле (`he42.LENS_K1_WIDE`, оценка, не замер); задник 16 м, человек 14 м, камера на 2,2 м над полом сцены | Плоский сдвиг панорамы совпадал с моделью регулятора по построению и не мог показать ошибки геометрии. У живой камеры при том же °/с картинка у края кадра едет быстрее (на широком угле ×1,25 к центру), а центр — на 10% медленнее, чем «fw/s × угол обзора»; наклон даёт трапецию, ходьба к камере меняет размер. Карта remap — по сетке 8 px: 1280×720 ~7 мс на кадр при движущейся камере |

## Чёрный ящик, повтор и доступ агента (шаг А)

| Решение | Почему |
|---|---|
| Буфер 5 мин (настройка зажата в 60–900 с), кадры 5 к/с, JPEG q70, не больше 640×360 | Плохой момент замечают через минуту-две; zip одного эпизода ~2,5 МБ на 30 с, значит 5 мин JPEG 640×360 в памяти — около 25 МБ (оценка, не замер). | Очередь кадров до сжатия — 50 (~10 с при 5 к/с) | В очереди лежат полные кадры (1920×1080 — ~6 МБ): прежние 2000 при зависшем фоновом потоке заняли бы гигабайты |
| `--lab record` — только запросы, без стопов (`observe_only`) | Ноутбук — второй клиент камеры, которую может вести программа на Windows в эфире: наш стоп остановил бы камеру, а та не повторила бы тот же код скорости (`only_if_changed`) |
| Запись не бросает исключений и не блокирует (`safe_event`/`safe_frame`) | Слежение и аварийные стопы важнее записи |
| Пароли вырезаются: `redact_url` понимает «@» внутри пароля; ключи `pass/pwd/secret/token` в метаданных и строках событий удаляются | Zip уходит разработчику; один найденный пароль в zip — утечка |

| Повтор воспроизводит записанные коды точно (0 расхождений на 675 тактах); `follow on` хранит применённую `video_latency`; повреждённые строки пропускаются и считаются | Иначе «стало» нельзя честно сравнивать с «было»; запись, оборванная выключением питания, всё равно читается |
| API слушает только 127.0.0.1, токен Bearer в `config.json` (`api_token`), чтение по умолчанию | Управление камерой в эфир не должно быть доступно по сети; токен защищает от других программ на этом компьютере |
| Любая команда, способная двинуть камеру, требует ОБА флажка: «Разрешить управление агенту» и «Камера НЕ в эфире» (спека §4); `/follow off` — только первый | Агенту нельзя доверить эфир; остановить слежение безопасно всегда, включить — нет |

| `--lab`: коды выхода 0/1/2/3/4/130, последняя строка всегда `RESULT {json}`, вывод очищается от паролей, `--ip sim` для пробы | Агенту нужен машинно разбираемый итог и безопасный пробный прогон; движение только с `--not-on-air` |

| Tally показан рамкой вокруг видео, как на мультивьюере ATEM | Оператор смотрит на видео, рамка видна периферийным зрением |
| Tally «в эфире / не в эфире» только после TlIn с последнего hello, иначе «неизвестно» | Ложное «не в эфире» позволило бы двигать живую камеру |
| Tally только показывает эфир и ничего не блокирует | Решение пользователя (2026-10-22): защиту эфира держат флажки оператора, Tally — подсказка для глаз |
| Цвета — только в `ui/theme.py` (охраняет `test_no_hardcoded_colors`), основные размеры — там же | Прежде цвета были разбросаны по виджетам и расходились |
