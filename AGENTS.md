# PTZ Tracker — для агента

Windows-программа (PySide6), которая ведёт докладчика PTZ-камерой Panasonic AW-HE42 по сети. Пользователь — оператор трансляций, не программист; общение и интерфейс — на русском. Разработка идёт на macOS. **С машины разработчика живая камера недоступна:** всё проверяется на симуляторе (`sim/`), а реальные факты приходят от пользователя через «Диагностику камеры» (zip-отчёт) и скриншоты.

## Что читать и когда

- `docs/ARCHITECTURE.md` — перед изменением структуры, потоков, единиц измерения или путей команд к камере; там же инварианты безопасности.
- `docs/DECISIONS.md` — перед тем как менять любой порог, коэффициент, поток видео или приоритет: у каждого значения есть замер-причина.
- `docs/BACKLOG.md` — при выборе следующей работы: этап 4, отложенное, открытые вопросы.
- `docs/superpowers/specs/2026-10-19-ptz-tracker-design.md` — исходный дизайн; §7 — факты живой камеры.
- `docs/superpowers/plans/` — выполненные планы этапов 1–3 (образец формата для новых).

## Команды

```bash
python3 -m venv .venv && .venv/bin/pip install -e ".[dev]"   # Python 3.12–3.13
.venv/bin/pytest -q -m "not slow"     # быстрый набор, ~1 мин — после каждого изменения
.venv/bin/pytest -q                   # полный, ~9 мин (реальное время на симуляторе) — перед коммитом этапа
.venv/bin/ruff check src tests        # линтер (F, E9, B, I); --fix сортирует импорты
.venv/bin/python -m ptztracker --sim  # окно с виртуальной камерой
```

`.exe` собирается только на Windows: `build.bat` или CI `.github/workflows/windows-build.yml`. На Mac `pyinstaller packaging/ptztracker.spec` годится лишь для проверки spec. Первый запуск свежей сборки длится 15–30 с — это не зависание.

## Как вести работу

- **Новая функция:** обсуждение → спека → план в `docs/superpowers/` → TDD задачами → независимое ревью всей ветки в конце. Пользователь одобряет план до кода. Работа идёт в ветке `main`.
- **Сначала тест, который падает.** Поведение регулятора — сначала в виртуальном времени (`tests/control/loop.py`, умеет `speed_factor` и `cmd_delay`), затем на симуляторе в реальном времени (с пометкой `@pytest.mark.slow`).
- **Новые факты о живой камере** записывайте в §7 спеки и в `camera/he42.py`: это единственный источник замеров для модели и симулятора.
- **Изменение ради замера** (порог, коэффициент): причина и цифры идут в `docs/DECISIONS.md`, а то, что отложено, — в `docs/BACKLOG.md`.
- **Сообщения пользователю** — простым языком, с тем, что ему сделать на площадке (пересобрать, откалибровать, прислать отчёт).

## Инварианты, которые держат тесты

- Любое ручное действие, Esc, смена камеры, остановка анализа или раскачка выключают слежение **до** отправки следующей команды.
- Аварийный стоп и стопы при выключении слежения никогда не теряются (`camera/scheduler.py`).
- Поток Qt не ждёт сеть и нейросеть: фоновые потоки, UI читает снимки состояния по таймеру.
- Пароли не попадают в логи, на экран и в отчёты.

## Ловушки, которых не видно в коде

- Ключевые точки — numpy float32: перед арифметикой со знаками приводите к `float`.
- Положение камеры в модели — `CameraDynamics.position(t)`. Старые команды сворачиваются, поэтому `displacement(0, t)` после 10 с неверно.
- `Frame.t_capture` — момент *получения* кадра; задержку видео вычитает регулятор (`Calibration.video_latency`).
- Симулятор совпадает с моделью регулятора по построению: устойчивость к ошибкам калибровки проверяет только виртуальный стенд с `speed_factor`.
- Интерфейс должен помещаться в окно ~1640×850: правая панель прокручивается.
- Модель YOLO под AGPL-3.0 — только для внутреннего использования.
